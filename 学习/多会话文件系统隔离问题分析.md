# 多会话文件系统隔离问题分析

## 🎯 核心问题

当多个 Sandbox（会话）共享同一个 Workspace（PVC/Volume）时：
- 文件系统**没有隔离**
- 会话之间**可以互相访问和修改**文件
- **会发生**误操作或冲突
- **OpenClaw 原生没有**处理这个问题的机制

---

## 🔍 问题详解

### 共享 Workspace 的现实

```
┌─────────────────────────────────────────────────────────────┐
│  共享 Workspace (PVC/Volume)                                │
│  /workspace/                                                │
│    ├── script.py      ← 会话 1 创建                         │
│    ├── data.csv       ← 会话 2 创建                         │
│    └── output.txt     ← 会话 1 创建                         │
│                                                             │
│  ┌──────────────┐          ┌──────────────┐                │
│  │ Sandbox 1    │          │ Sandbox 2    │                │
│  │ (会话 1)     │          │ (会话 2)     │                │
│  │              │          │              │                │
│  │ 可以访问：   │          │ 可以访问：   │                │
│  │ - script.py  │          │ - script.py  │  ← 同样的文件！ │
│  │ - data.csv   │          │ - data.csv   │                │
│  │ - output.txt │          │ - output.txt │                │
│  └──────────────┘          └──────────────┘                │
└─────────────────────────────────────────────────────────────┘
```

### 可能发生的冲突场景

| 场景 | 描述 | 后果 |
|------|------|------|
| **误删除** | 会话 1 执行 `rm -rf /workspace/*` | 会话 2 的文件也没了 |
| **并发写入** | 两个会话同时写同一个文件 | 数据损坏或丢失 |
| **覆盖文件** | 会话 2 创建同名文件覆盖会话 1 的 | 会话 1 的数据丢失 |
| **环境污染** | 会话 1 安装的依赖影响会话 2 | 意外的行为 |

### 具体示例

```bash
# 会话 1 正在处理数据
$ python process.py --output result.csv
# 生成了 result.csv

# 与此同时，会话 2（用户可能忘了）
$ rm *.csv
# 想清理自己的文件，结果把会话 1 的也删了！

# 会话 1 继续
$ cat result.csv
cat: result.csv: No such file or directory
# 文件不见了！
```

## 🤔 这是特性还是问题？

### 取决于使用场景

| 场景 | 共享是特性 ✅ | 共享是问题 ❌ |
|------|-------------|-------------|
| 用户想在新会话继续之前的工作 | ✅ | |
| 多个会话协作处理同一个项目 | ✅ | |
| 会话 1 创建的脚本，会话 2 想用 | ✅ | |
| 两个会话同时修改同一个文件 | | ❌ |
| 一个会话误删了另一个会话的文件 | | ❌ |
| 想让每个会话完全独立 | | ❌ |

### OpenClaw 的设计哲学

```
┌─────────────────────────────────────────────────────────────┐
│  OpenClaw 的假设：                                          │
│                                                             │
│  "我是 Alice 的个人助手"                                     │
│  "所有会话都是 Alice 的"                                     │
│  "Alice 对自己的文件负责"                                    │
│                                                             │
│  类比：                                                      │
│  就像你用自己的电脑开多个终端窗口：                            │
│  - 它们共享文件系统                                          │
│  - 你在一个终端删了文件，另一个终端也看不到了                   │
│  - 这是你自己的责任                                          │
│                                                             │
│  OpenClaw 关注的是：                                         │
│  ✅ 安全隔离（防止恶意代码影响主机）                          │
│  ✅ 资源限制（防止滥用）                                     │
│  ❌ 会话间冲突（不在设计范围内）                              │
└─────────────────────────────────────────────────────────────┘
```

## 🛠️ 解决方案

### 方案 1：接受共享（最简单）

**理念**：这是同一个用户的多个会话，共享是合理的

**实现**：
- 不做任何改动
- 在 UI 上明确提示"共享工作区"
- 教育用户理解这个模型

**适用场景**：
- 用户理解并期望共享
- 任务之间有依赖关系
- 需要延续之前的工作

**风险缓解**：
```
1. UI 提示：
   ┌────────────────────────────────────────┐
   │ ⚠️ 所有会话共享同一个工作空间           │
   │ 文件修改会影响其他会话                  │
   └────────────────────────────────────────┘

2. 提供回收站功能（延迟删除）

3. 提供版本历史/快照功能

4. 重要操作前确认
```

---

### 方案 2：会话级子目录隔离（推荐）

**理念**：每个会话有自己的子目录，但可以访问共享区

**目录结构**：
```
/workspace/
├── .shared/                 ← 显式共享区（用户主动共享）
│   ├── datasets/
│   ├── models/
│   └── templates/
│
├── sessions/
│   ├── session-001/         ← 会话 1 的私有目录（默认工作目录）
│   │   ├── script.py
│   │   └── output.txt
│   │
│   ├── session-002/         ← 会话 2 的私有目录
│   │   ├── analysis.py
│   │   └── result.csv
│   │
│   └── session-003/
│       └── ...
```

**实现代码**：

```typescript
// K8s Sandbox 创建时设置会话专属目录
async function createSandbox(sessionId: string) {
  const sessionDir = `/workspace/sessions/${sessionId}`;
  const sharedDir = `/workspace/.shared`;

  const pod = {
    spec: {
      initContainers: [{
        name: 'setup-dirs',
        image: 'busybox',
        command: ['sh', '-c', `
          mkdir -p ${sessionDir}
          mkdir -p ${sharedDir}
          chown 1000:1000 ${sessionDir}
        `],
        volumeMounts: [{
          name: 'workspace',
          mountPath: '/workspace',
        }],
      }],

      containers: [{
        name: 'sandbox',
        image: 'openclaw-sandbox:latest',

        // 关键：设置工作目录为会话专属目录
        workingDir: sessionDir,

        env: [
          { name: 'SESSION_DIR', value: sessionDir },
          { name: 'SHARED_DIR', value: sharedDir },
          { name: 'SESSION_ID', value: sessionId },
        ],

        volumeMounts: [{
          name: 'workspace',
          mountPath: '/workspace',
        }],
      }],
    },
  };

  return pod;
}
```

**用户体验**：
```bash
# 会话 1
$ pwd
/workspace/sessions/session-001

$ echo "hello" > greeting.txt
$ ls
greeting.txt

# 会话 2
$ pwd
/workspace/sessions/session-002

$ ls
(空的，看不到会话 1 的文件)

# 如果需要共享
$ cp ../session-001/greeting.txt .
# 或者
$ cp greeting.txt /workspace/.shared/
```

**优点**：
- ✅ 默认隔离，减少误操作
- ✅ 仍可访问共享区（显式操作）
- ✅ 仍可跨会话访问（如果需要）
- ✅ 实现简单

**缺点**：
- ❌ 路径变复杂
- ❌ 需要改 OpenClaw 或 Sandbox 启动逻辑

### 方案 3：完全隔离 + 显式共享

**理念**：每个会话完全独立的存储，需要共享时显式操作

**架构**：
```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  ┌────────────────┐    ┌────────────────┐                   │
│  │ Sandbox 1      │    │ Sandbox 2      │                   │
│  │ PVC: sess-001  │    │ PVC: sess-002  │   ← 独立的 PVC    │
│  │ /workspace/    │    │ /workspace/    │                   │
│  │ (完全独立)     │    │ (完全独立)     │                   │
│  └───────┬────────┘    └───────┬────────┘                   │
│          │                     │                             │
│          └──────────┬──────────┘                             │
│                     ↓                                        │
│  ┌─────────────────────────────────────────┐                │
│  │          用户共享存储 (PVC)              │                │
│  │          /user-shared/                  │   ← 显式挂载    │
│  │  需要共享时：                            │                │
│  │  cp /workspace/file.txt /user-shared/   │                │
│  └─────────────────────────────────────────┘                │
└──────────────────────────────────────────────────────────────┘
```

**实现**：

```yaml
# 每个会话的 Sandbox Pod
spec:
  volumes:
    # 会话专属存储（临时）
    - name: session-workspace
      emptyDir:
        sizeLimit: 1Gi

    # 用户共享存储（持久）
    - name: user-shared
      persistentVolumeClaim:
        claimName: user-shared-pvc

  containers:
    - name: sandbox
      volumeMounts:
        - name: session-workspace
          mountPath: /workspace        # 私有，会话结束后销毁
        - name: user-shared
          mountPath: /shared           # 共享，持久化
```

**优点**：
- ✅ 完全隔离，零冲突风险
- ✅ 共享是显式的，用户有意识
- ✅ 私有空间会话结束自动清理

**缺点**：
- ❌ 不方便（每次都要手动共享）
- ❌ 会话结束私有数据丢失（除非显式保存）
- ❌ 无法延续之前会话的工作

### 方案 4：Copy-on-Write 模式

**理念**：每个会话看到相同的初始状态，但修改是隔离的

**原理**：
```
用户基础 Workspace (只读)
    /workspace-base/
        ├── datasets/
        └── templates/
              ↓ OverlayFS
┌──────────────────────────────────────────────────────────────┐
│  Sandbox 1                     Sandbox 2                     │
│  /workspace/ (overlay)         /workspace/ (overlay)         │
│                                                              │
│  Lower: /workspace-base (只读，共享)                         │
│  Upper: /session-001 (读写，独立)   /session-002 (独立)       │
│                                                              │
│  效果：                                                       │
│  - 看到相同的基础文件                                         │
│  - 修改只影响自己的 Upper 层                                  │
│  - 不会互相干扰                                               │
│  - 删除文件只是在 Upper 层标记"已删除"                        │
└──────────────────────────────────────────────────────────────┘
```

**实现**（需要特权容器）：

```yaml
spec:
  initContainers:
    - name: setup-overlay
      image: busybox
      securityContext:
        privileged: true  # 需要特权
      command:
        - sh
        - -c
        - |
          mkdir -p /overlay/upper /overlay/work /merged
          mount -t overlay overlay \
            -o lowerdir=/base,upperdir=/overlay/upper,workdir=/overlay/work \
            /merged
      volumeMounts:
        - name: base-workspace
          mountPath: /base
          readOnly: true
        - name: session-overlay
          mountPath: /overlay
        - name: merged-workspace
          mountPath: /merged
```

**优点**：
- ✅ 优雅的隔离
- ✅ 共享基础数据，节省空间
- ✅ 对用户透明（看起来像完整的文件系统）

**缺点**：
- ❌ 需要特权容器（安全风险）
- ❌ 实现复杂
- ❌ 不是所有存储/环境都支持

### 方案 5：文件锁机制

**理念**：允许共享，但通过锁防止并发冲突

**实现**：

```typescript
class FileLock {
  private lockDir = '/workspace/.locks';

  async acquireLock(filePath: string, sessionId: string): Promise<boolean> {
    const lockFile = `${this.lockDir}/${this.hash(filePath)}.lock`;

    try {
      // 创建锁文件，写入 sessionId 和时间戳
      await fs.writeFile(lockFile, JSON.stringify({
        sessionId,
        filePath,
        lockedAt: new Date().toISOString(),
      }), { flag: 'wx' }); // wx = 排他创建

      return true;
    } catch (e) {
      // 锁已存在，检查是否过期
      const lockInfo = JSON.parse(await fs.readFile(lockFile, 'utf-8'));
      const age = Date.now() - new Date(lockInfo.lockedAt).getTime();

      if (age > 300000) { // 5分钟过期
        await fs.unlink(lockFile);
        return this.acquireLock(filePath, sessionId);
      }

      console.log(`File ${filePath} locked by session ${lockInfo.sessionId}`);
      return false;
    }
  }

  async releaseLock(filePath: string, sessionId: string): Promise<void> {
    const lockFile = `${this.lockDir}/${this.hash(filePath)}.lock`;

    try {
      const lockInfo = JSON.parse(await fs.readFile(lockFile, 'utf-8'));
      if (lockInfo.sessionId === sessionId) {
        await fs.unlink(lockFile);
      }
    } catch (e) {
      // 锁不存在，忽略
    }
  }

  private hash(str: string): string {
    return crypto.createHash('md5').update(str).digest('hex');
  }
}
```

**优点**：
- ✅ 防止并发写入冲突
- ✅ 不改变目录结构

**缺点**：
- ❌ 不防止误删
- ❌ 锁管理复杂（过期、死锁）
- ❌ 需要改 OpenClaw 或包装层

## 🎯 推荐实施路径

### 阶段 1：接受共享 + UI 提示（MVP）

```
1. 不改动文件系统结构
2. 在 UI 明确提示共享行为
3. 添加基础保护：
   - 回收站（延迟删除）
   - 危险操作确认
```

### 阶段 2：会话子目录隔离（推荐）

```
1. 每个会话默认工作目录：/workspace/sessions/{sessionId}/
2. 共享区：/workspace/.shared/
3. 用户可以：
   - 在自己目录自由操作
   - 显式复制到共享区
   - 需要时访问其他会话（知道路径）
```

**配置示例**：

```yaml
# OpenClaw 配置
sandbox:
  workspace:
    mode: "session-isolated"  # 或 "shared"
    sessionDir: "/workspace/sessions/${SESSION_ID}"
    sharedDir: "/workspace/.shared"
    # 会话结束后保留多久
    retentionDays: 7
```

### 阶段 3：高级隔离（可选）

根据用户反馈和需求，考虑：
- Copy-on-Write
- 完全独立存储
- 更复杂的权限控制

## 💡 最佳实践建议

### 1. 命名规范

```
/workspace/
├── .shared/              # 前缀 . 表示特殊目录
├── .trash/               # 回收站
├── sessions/
│   ├── 2024-02-06_task1/ # 包含日期，便于清理
│   └── 2024-02-06_task2/
```

### 2. 自动清理

```typescript
// 定期清理过期会话目录
async function cleanupOldSessions(retentionDays: number) {
  const sessionsDir = '/workspace/sessions';
  const now = Date.now();
  const maxAge = retentionDays * 24 * 60 * 60 * 1000;

  const sessions = await fs.readdir(sessionsDir);

  for (const session of sessions) {
    const stat = await fs.stat(`${sessionsDir}/${session}`);
    const age = now - stat.mtimeMs;

    if (age > maxAge) {
      // 移到回收站或直接删除
      await fs.rename(
        `${sessionsDir}/${session}`,
        `/workspace/.trash/${session}`
      );
    }
  }
}
```

## 📚 总结

### 核心结论

| 问题 | 答案 |
|------|------|
| 多 Sandbox 文件系统隔离吗？ | **不隔离**，共享同一个存储 |
| 会发生误操作吗？ | **会**，一个会话可以影响另一个 |
| OpenClaw 有处理机制吗？ | **没有**，这是设计上的选择 |
| 怎么解决？ | **会话子目录隔离**（推荐）|

### 核心理解

```
共享 Workspace 是设计选择，不是 bug。

就像同一台电脑上的多个终端窗口共享文件系统，
这是为了方便用户在不同会话间延续工作。

如果需要隔离，需要在应用层实现：
- 会话子目录（推荐）
- 完全独立存储
- Copy-on-Write
```
