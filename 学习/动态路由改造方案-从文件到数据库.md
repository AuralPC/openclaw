# 动态路由改造方案：从文件到数据库

> 核心问题：OpenClaw 目前的 Agent 注册和路由规则全部存储在一个本地 JSON5 配置文件中。当用户量增长到数千甚至上万时，这个文件会成为瓶颈。本文分析如何将 Agent 和路由数据从配置文件迁移到数据库，实现真正的动态路由。

---

## 一、先搞清楚现在的配置是怎么工作的

### 1.1 配置文件长什么样

OpenClaw 的所有配置都在一个 JSON5 文件里（通常是 `~/.openclaw/openclaw.json`）。里面的内容大致可以分成两类：

```
openclaw.json
│
├── 【低频变动的配置】
│     ├── 模型设置（用哪个 AI 模型、API 密钥配置）
│     ├── 渠道设置（WhatsApp/Telegram/你的前端渠道的配置）
│     ├── 沙箱设置（Docker 沙箱的参数）
│     ├── 工具设置（哪些工具开放、哪些禁用）
│     └── 网关设置（端口、TLS、日志等）
│
└── 【高频变动的配置】  ← 这是问题所在
      ├── agents.list（所有 Agent 的注册列表）
      │     每注册一个用户就要加一条
      │
      └── bindings（所有路由绑定规则）
            每注册一个用户就要加一条
```

在"一个用户一个 Agent"的方案里，每新增一个用户，就要往这个文件里写入两条数据（一条 Agent 注册 + 一条路由绑定）。1000 个用户 = 2000 条记录。10000 个用户 = 20000 条记录。全部塞在一个 JSON 文件里。

### 1.2 配置文件被读取的频率

这是关键信息：**OpenClaw 几乎在处理每一条消息时都会重新读取配置文件。**

具体来说，系统内部有一个叫 `loadConfig()` 的函数，它被整个代码库的大约 **270 个地方**调用。每次有消息进来、要解析路由、要检查权限、要查 Agent 信息，都会调用它。

不过，系统做了一个简单的缓存优化：

```
loadConfig() 的工作方式：

  调用 loadConfig()
      │
      ├── 缓存有效吗？（200 毫秒内读过？）
      │     │
      │     ├── 是 → 直接返回缓存的配置（不读磁盘）
      │     │
      │     └── 否 → 从磁盘读取文件
      │              → 解析 JSON5
      │              → 校验格式
      │              → 填充默认值
      │              → 存入缓存（有效期 200 毫秒）
      │              → 返回配置
      │
      └── 缓存被清除的时机：
            - 配置文件被写入时（writeConfigFile）
            - 缓存过期（200 毫秒后）
```

也就是说，在 200 毫秒内的多次读取只会读一次磁盘。但如果并发量高，每秒仍然会有多次磁盘读取。当配置文件从几 KB 膨胀到几 MB 时，这个读取+解析的开销就不可忽视了。

### 1.3 配置文件被写入的频率

写入就更麻烦了。`writeConfigFile()` 被大约 **63 个地方**调用，每次写入会：

1. 校验整个配置
2. 写入临时文件
3. 做最多 5 个版本的备份轮转
4. 原子重命名
5. 清除缓存

在"每注册一个用户就写一次配置文件"的方案里，如果 10 个用户同时注册，就是 10 次全量写入。每次写入都是整个配置文件的完整内容——不管你只改了一个 Agent，整个文件都要重新序列化和写入。

## 二、为什么要改成数据库

| 维度 | 配置文件 | 数据库 |
|------|---------|-------|
| **读取性能** | 每次读取整个文件并解析 | 只查询需要的记录 |
| **写入性能** | 每次写入整个文件 | 只插入/更新一条记录 |
| **并发安全** | 需要自己加文件锁 | 数据库自带事务和锁 |
| **查询能力** | 无（必须全量加载再过滤） | 有索引，可以精确查询 |
| **数据规模** | 几千条开始吃力 | 百万条轻松 |
| **原子性** | 弱（文件写入可能中断） | 强（事务保证） |

**用一句话说：配置文件适合存"少量、低频变动的系统级设置"，不适合存"大量、高频变动的业务数据"。**

Agent 列表和路由规则在多用户场景下就是业务数据，应该放在数据库里。

---

## 三、改造策略：不是全部迁移，而是分层拆分

最关键的设计决策是：**不需要把整个配置文件都搬进数据库。**

配置文件里的内容天然分成两类，应该区别对待：

### 留在配置文件里的（系统配置）

```
这些东西很少变动，而且跟具体用户无关：

  ├── 模型提供商设置（API 密钥、模型列表）
  ├── 渠道设置（你的前端渠道插件的全局配置）
  ├── 沙箱默认设置（Docker 参数、默认权限）
  ├── 工具全局设置（哪些工具全局开放/禁用）
  ├── 网关设置（端口、TLS、日志级别）
  └── Agent 默认设置（默认模型、默认超时时间等）
```

这些配置可能一个月才改一次，文件存储完全够用。

### 迁移到数据库的（业务数据）

```
这些东西随用户数量线性增长，而且频繁变动：

  ├── agents.list（Agent 注册列表）
  │     → 每个用户一条记录
  │     → 包含：agentId, name, workspace, model, tools, sandbox 等
  │
  └── bindings（路由绑定规则）
        → 每个用户至少一条记录
        → 包含：agentId, channel, accountId, peer 等匹配条件
```

## 四、改造方案详解

### 4.1 核心思路：在配置加载层做一次"合并"

整个改造的核心思路是：

> 保持 `loadConfig()` 的接口不变，让它返回的配置对象中，`agents.list` 和 `bindings` 部分来自数据库，其他部分仍然来自文件。

```
改造前：
  loadConfig() → 读文件 → 返回完整配置

改造后：
  loadConfig() → 读文件（系统配置部分）
               → 查数据库（Agent 列表 + 路由规则）
               → 合并成一个完整配置对象
               → 返回
```

这样做的巨大好处是：**270 个调用 `loadConfig()` 的地方完全不需要改动。** 它们拿到的还是同样结构的配置对象，只是数据的来源变了。

### 4.2 数据库表设计（逻辑层面）

需要两张核心表：

**Agent 表**

```
agents 表
┌──────────┬──────────┬─────────────────────┬───────────┬────────────┐
│ agent_id │ name     │ workspace           │ model     │ config_json│
├──────────┼──────────┼─────────────────────┼───────────┼────────────┤
│ user-001 │ 小明助手  │ /data/ws/user-001   │ claude... │ {tools...} │
│ user-002 │ 小红助手  │ /data/ws/user-002   │ claude... │ {tools...} │
│ user-003 │ 小刚助手  │ /data/ws/user-003   │ claude... │ {sandbox}  │
└──────────┴──────────┴─────────────────────┴───────────┴────────────┘

  agent_id:    主键，对应 OpenClaw 的 agentId
  name:        显示名称
  workspace:   Workspace 目录路径
  model:       使用的 AI 模型
  config_json: 该 Agent 的其他配置（工具权限、沙箱设置等），JSON 格式
```

**路由绑定表**

```
bindings 表
┌────┬──────────┬──────────┬────────────┬──────────┬──────────┐
│ id │ agent_id │ channel  │ account_id │ peer_kind│ peer_id  │
├────┼──────────┼──────────┼────────────┼──────────┼──────────┤
│ 1  │ user-001 │ my-chat  │ default    │ dm       │ user-001 │
│ 2  │ user-002 │ my-chat  │ default    │ dm       │ user-002 │
│ 3  │ user-003 │ my-chat  │ default    │ dm       │ user-003 │
└────┴──────────┴──────────┴────────────┴──────────┴──────────┘

  agent_id:    指向 agents 表
  channel:     渠道 ID（你的前端渠道）
  account_id:  渠道账号（多实例时区分）
  peer_kind:   匹配类型（dm/group/channel）
  peer_id:     匹配的对端标识（用户 ID）
```

### 4.3 合并后的 loadConfig() 工作流

```
调用 loadConfig()
      │
      ├── 缓存有效吗？
      │     │
      │     ├── 是 → 返回缓存
      │     │
      │     └── 否 ↓
      │
      ├── 1. 从磁盘读取系统配置文件
      │       → 模型设置、渠道设置、沙箱默认值...
      │       → 不包含 agents.list 和 bindings
      │
      ├── 2. 从数据库查询 Agent 列表
      │       → SELECT * FROM agents
      │       → 转换成 OpenClaw 格式的 agents.list 数组
      │
      ├── 3. 从数据库查询路由绑定
      │       → SELECT * FROM bindings
      │       → 转换成 OpenClaw 格式的 bindings 数组
      │
      ├── 4. 合并成一个完整的配置对象
      │       → { ...文件配置, agents: { list: 数据库结果 }, bindings: 数据库结果 }
      │
      ├── 5. 存入缓存
      │
      └── 6. 返回
```

### 4.4 路由解析的优化

当前的路由解析是这样的：

```
现在：
  收到消息 → loadConfig() 拿到完整配置（包含所有用户的绑定规则）
           → 遍历所有绑定规则，逐条匹配
           → 找到匹配的 Agent
```

10000 个用户 = 遍历 10000 条绑定规则。虽然匹配逻辑很简单（就是字符串比较），但也是浪费。

改成数据库之后，可以优化成：

```
优化后：
  收到消息（channel="my-chat", peer="user-001"）
           → 直接查数据库：
             SELECT agent_id FROM bindings
             WHERE channel='my-chat' AND peer_id='user-001'
           → 一条 SQL，精确命中
```

不过这个优化不是必须的。因为路由解析函数 `resolveAgentRoute()` 接收的是配置对象，不直接访问数据源。如果你不想改它的内部逻辑，仍然可以走"合并配置 → 遍历匹配"的方式，只是数据来源从文件变成了数据库。

更进一步的优化是：**跳过 loadConfig()，在路由解析时直接查数据库**。这需要改动 `resolveAgentRoute()` 函数，但性能提升最大。

## 五、需要处理的四个关键问题

### 问题一：缓存策略

现在的 200 毫秒缓存是基于文件的——200 毫秒内不重复读文件。换成数据库后，同样的思路可以继续用：

```
选项 A：保持 200 毫秒缓存（最简单）
  - 200 毫秒内的所有请求用缓存
  - 新注册的用户最多 200 毫秒后才能被路由命中
  - 对用户无感知（200 毫秒的延迟人根本察觉不到）

选项 B：事件驱动缓存失效
  - 数据库写入时发一个通知（比如 Redis Pub/Sub）
  - Gateway 收到通知后清除缓存
  - 下次请求时重新从数据库加载
  - 实时性更好，但架构更复杂

选项 C：分层缓存
  - Agent 列表：缓存 5 秒（不经常变）
  - 路由规则：缓存 5 秒（不经常变）
  - 系统配置：缓存 60 秒（几乎不变）
  - 平衡性能和实时性
```

对于多用户产品来说，选项 A 已经足够。用户注册后等 200 毫秒再开始聊天，完全不是问题。

### 问题二：配置写入的替换

现在创建 Agent 时，最终调用 `writeConfigFile()` 把整个配置写回文件。改造后，这个函数需要分流：

```
改造后的"写入配置"逻辑：

  写入内容是 Agent 或 Binding？
      │
      ├── 是 → 写入数据库
      │         INSERT INTO agents VALUES (...)
      │         INSERT INTO bindings VALUES (...)
      │         清除缓存
      │
      └── 否 → 继续写入配置文件（系统配置的修改仍走文件）
```

### 问题三：配置文件热重载的替换

OpenClaw 有一个文件监听器，当配置文件变化时自动重载相关组件（重启渠道、刷新钩子等）。

改成数据库后，Agent 和 Binding 的变化不再触发文件变化。需要一个替代的通知机制：

```
现在：
  文件变化 → chokidar 监听到 → 触发组件重载

改造后选项：
  A. 定时轮询数据库（简单，但有延迟）
  B. 数据库变更通知（比如 PostgreSQL 的 LISTEN/NOTIFY）
  C. 应用层事件（写入数据库后主动触发重载）
```

不过对于 Agent 和 Binding 来说，**可能根本不需要热重载**。因为现在的 `loadConfig()` 本身就是每次都重新读取（带 200 毫秒缓存），所以数据库里的变化会在缓存过期后自动生效。热重载主要是给"修改了渠道配置需要重连"这种场景用的，Agent 列表的变化不需要触发任何组件重启。

### 问题四：既有 Agent 的兼容

改造后，配置文件里可能仍然留着一些 Agent（比如系统级的默认 Agent）。需要一个合并策略：

```
合并规则：
  最终的 agents.list = 配置文件中的 Agent + 数据库中的 Agent
  最终的 bindings   = 配置文件中的绑定 + 数据库中的绑定

冲突处理：
  如果同一个 agentId 在文件和数据库中都存在 → 数据库优先
  如果同一条绑定规则在文件和数据库中都存在 → 数据库优先
```

这样你可以在配置文件里保留一个默认的 "main" Agent（用于系统管理），同时所有用户 Agent 都在数据库里。

## 六、改造工作量评估

### 必须改的

| 改动项 | 说明 | 影响范围 |
|--------|------|---------|
| **改造 loadConfig()** | 让它从"纯文件读取"变成"文件 + 数据库合并读取" | 1 个函数，但影响全局（270 个调用点自动受益） |
| **改造 writeConfigFile()** | 写入 Agent/Binding 时走数据库，其他仍走文件 | 1 个函数，涉及 63 个调用点的分流逻辑 |
| **新建数据库表** | agents 表 + bindings 表 | 新增 |
| **新建数据库访问层** | 封装数据库的增删改查操作 | 新增 |
| **调整缓存逻辑** | 数据库结果的缓存策略 | 改动现有缓存机制 |

### 可选优化

| 改动项 | 说明 | 收益 |
|--------|------|------|
| 路由解析直接查数据库 | 跳过 loadConfig()，直接 SQL 查询 | 大规模用户下性能大幅提升 |
| Agent 信息按需加载 | 不一次性加载所有 Agent，按 agentId 单条查询 | 减少内存占用 |
| 数据库连接池 | 复用数据库连接，减少连接开销 | 高并发下性能提升 |

### 完全不需要改的

| 模块 | 为什么不需要改 |
|------|-------------|
| 路由解析逻辑（resolveAgentRoute） | 它只操作传入的配置对象，不关心数据来源 |
| Agent 运行逻辑 | 它只需要 agentId 和 workspace 路径，不关心注册数据在哪 |
| Session 管理 | 独立于配置存储 |
| 沙箱系统 | 独立于配置存储 |
| 渠道插件 | 独立于配置存储 |
| 子 Agent 系统 | 独立于配置存储 |

**这就是改造代价最小的原因：OpenClaw 的架构中，配置加载是一个集中的、单一的入口（`loadConfig()`）。** 你只需要改这一个入口的内部实现，整个系统的其他部分都感知不到变化。

## 七、改造的分阶段路径

### 阶段一：最小可行改造

**只迁移 Agent 列表和路由绑定到数据库。**

```
loadConfig() 内部：
  1. 照常读取配置文件
  2. 从数据库查询 agents 和 bindings
  3. 用数据库结果替换配置中的 agents.list 和 bindings
  4. 返回合并后的配置

writeConfigFile() 内部：
  如果写入涉及 agents 或 bindings → 写数据库
  否则 → 照常写文件
```

这个阶段：
- 开发量最小
- 风险最低（系统配置完全不受影响）
- 已经解决了核心问题（大量用户的注册和路由）

### 阶段二：性能优化

**让路由解析直接查数据库，不再经过 loadConfig()。**

```
收到消息（channel="my-chat", peer="user-001"）
    │
    ├── 直接查数据库：
    │     SELECT agent_id FROM bindings
    │     WHERE channel='my-chat' AND peer_id='user-001'
    │     LIMIT 1
    │
    └── 如果没命中 → 再走 loadConfig() 里的默认路由逻辑
```

这需要改动路由解析函数，但能消除"加载所有 Agent 到内存再遍历匹配"的开销。

### 阶段三：完全解耦（可选）

**把所有动态数据都迁移到数据库，配置文件只保留最核心的系统设置。**

```
配置文件只留：
  ├── 数据库连接信息
  ├── 网关基础设置（端口、TLS）
  └── 默认 Agent 设置

数据库存储：
  ├── Agent 注册（agents 表）
  ├── 路由绑定（bindings 表）
  ├── 模型配置（models 表）
  ├── 渠道配置（channels 表）
  └── 工具权限（tool_policies 表）
```

这是最终形态，但开发量大，而且大部分场景下阶段一就够用了。

## 八、数据库的选择

| 数据库 | 适用场景 | 优势 | 劣势 |
|--------|---------|------|------|
| **SQLite** | 单机部署、中小规模 | 零运维、嵌入式、文件级别存储 | 并发写入性能有限 |
| **PostgreSQL** | 生产环境、多实例 | 强事务、LISTEN/NOTIFY、JSON 支持 | 需要独立部署和运维 |
| **MySQL** | 生产环境 | 生态成熟、工具丰富 | JSON 支持不如 PostgreSQL |
| **Redis** | 缓存层或小型部署 | 极快读写、适合做路由缓存 | 持久化不如关系型数据库 |

**推荐：**
- 如果是单机部署、用户量在几千以内 → **SQLite**（OpenClaw 内部的记忆搜索已经在用 SQLite，技术栈一致）
- 如果是生产环境、用户量可能上万 → **PostgreSQL**
- 可以先用 SQLite 起步，后期迁移到 PostgreSQL（两者的 SQL 语法大部分兼容）

## 九、与"文件写入方案"的对比

回顾一下之前讨论过的"直接写入配置文件"方案，对比一下：

| 维度 | 文件写入方案 | 数据库方案 |
|------|-----------|-----------|
| **开发量** | 小（只需加一个 RPC 方法） | 中（需要改配置加载层 + 建表） |
| **性能上限** | 几千用户 | 几十万用户 |
| **并发安全** | 需要自己加文件锁 | 数据库自带 |
| **查询能力** | 无 | 有（可以按条件查 Agent、统计数量等） |
| **可维护性** | 低（万行 JSON 文件不好调试） | 高（数据库工具丰富） |
| **架构改动** | 几乎为零 | 需要改核心配置层 |
| **回退难度** | 容易（删掉 RPC 方法就行） | 中（需要恢复文件读取逻辑） |

**建议路径：**

```
起步阶段（几十~几百用户）
    → 用文件写入方案，快速验证产品

增长阶段（几百~几千用户）
    → 如果文件方案开始出现性能问题，启动数据库改造（阶段一）

规模化阶段（上万用户）
    → 完成数据库改造（阶段二），优化路由查询性能
```

不要过早优化。文件方案在中小规模下完全够用，而且开发成本远低于数据库方案。当你真正遇到瓶颈时再迁移，那时候你对系统的理解也会更深，改造会更稳。

## 十、总结

这次改造的本质是：

> **把配置文件从"系统配置 + 业务数据混合存储"拆分为"系统配置留在文件、业务数据迁入数据库"。**

OpenClaw 的架构为这种改造提供了一个非常友好的条件：**配置读取通过一个集中的入口函数（`loadConfig()`）进行，全系统约 270 个调用点都经过这一个入口。** 只要改了这个入口的内部实现，整个系统的其他部分——路由、Agent 运行、Session、沙箱、渠道——全部不需要改动。

这就像一栋大楼的供水系统：所有楼层的水龙头（270 个调用点）都连着同一根主管道（`loadConfig()`）。你要做的不是改每个水龙头，而是在主管道的源头，把水源从"水箱"（文件）换成"自来水厂"（数据库）。楼上的住户（业务逻辑）打开水龙头，照样有水用，根本不知道水源换了。
