# OpenClaw Multi-Agent 沟通机制详解

## 一、概述：Agent 之间是怎么"说话"的

在 OpenClaw 的多 Agent 体系中，每个 Agent 默认是**独立运行、互不干扰**的。它们各自有自己的会话、工具和工作空间，彼此之间看不到对方的内容。

但在实际使用中，Agent 之间经常需要协作——比如一个"总管 Agent"把复杂任务拆给"专家 Agent"去处理，或者两个 Agent 之间需要交换信息。OpenClaw 为此提供了**两套核心沟通机制**：

| 机制 | 对应工具 | 一句话概括 |
|------|---------|-----------|
| **直接对话** | `sessions_send` | 一个 Agent 给另一个 Agent 发消息，可以等回复，还能来回对话 |
| **派遣子代** | `sessions_spawn` | 一个 Agent 派出一个"分身"去干活，干完了自动汇报结果 |

这两套机制解决的问题不同、使用场景不同，但都遵循一个共同原则：**默认关闭，需要显式开启和授权**。

---

## 二、机制一：Agent 直接对话（sessions_send）

### 2.1 基本概念

`sessions_send` 就像是 Agent 之间的"即时通讯"。Agent A 可以给 Agent B 发一条消息，B 收到后处理并回复，A 再拿到回复。

这里有两个关键模式：

**模式一：发了就走（fire-and-forget）**
- Agent A 发消息给 Agent B
- 不等回复，立即继续自己的工作
- B 在后台处理，处理完了会通过"播报"机制把结果发出来

**模式二：发了等着（blocking）**
- Agent A 发消息给 Agent B
- 在指定时间内等待 B 的回复
- 拿到回复后继续工作

### 2.2 Ping-Pong 机制：来回对话

`sessions_send` 不仅仅是"发一条、回一条"这么简单，它还支持 **Ping-Pong（乒乓球）模式**——两个 Agent 可以来回对话多轮。

具体流程是这样的：

```
第1轮：A 发消息给 B
第2轮：B 回复 A，然后 A 再回复 B
第3轮：B 再回复 A，A 再回复 B
...
直到达到最大轮次，或者某一方主动喊停
```

**终止条件有两个：**
1. 达到最大对话轮次（默认 5 轮，最多 5 轮）
2. 任意一方回复 `REPLY_SKIP` 这个特殊关键词，表示"我没话说了，停吧"

**每一轮对话时，系统会自动注入上下文信息，告诉当前 Agent：**
- 你是发起方还是接收方
- 现在是第几轮，总共最多几轮
- 双方各自的会话标识

这样两个 Agent 就能像两个人聊天一样，来回讨论、逐步深入。

### 2.3 对话结束后的"播报"

Ping-Pong 对话结束后，系统还有一个**播报步骤（Announce）**：接收方 Agent 会收到一个总结性提示，要求它把这次对话的要点做个汇总，然后把汇总结果发送到它所在的频道。

接收方 Agent 如果觉得"没什么好播报的"，可以回复 `ANNOUNCE_SKIP` 来跳过这一步。

### 2.4 返回状态

`sessions_send` 执行后会返回一个状态码：

| 状态 | 含义 |
|------|------|
| `ok` | 成功，拿到了回复 |
| `accepted` | 消息已投递（发了就走模式） |
| `timeout` | 等回复超时了 |
| `error` | 执行过程中出错了 |
| `forbidden` | 没有权限，被策略拒绝了 |

## 三、机制二：派遣子代（sessions_spawn）

### 3.1 基本概念

`sessions_spawn` 更像是 Agent 的"分身术"。主 Agent 可以派出一个**子 Agent（Sub-Agent）**去执行一个具体的任务，子 Agent 在自己独立的会话中工作，完成后自动把结果汇报给主 Agent。

和 `sessions_send` 最大的区别在于：
- `sessions_send` 是两个**已存在的 Agent 之间**的对等对话
- `sessions_spawn` 是主 Agent **临时创建一个工作者**去干活

### 3.2 派遣过程

整个流程分为五个阶段：

**阶段一：派遣**
1. 主 Agent 调用 `sessions_spawn`，描述任务（"去研究一下 XX 主题"）
2. 系统自动生成一个全新的、独立的会话（session key 格式：`agent:某Agent:subagent:唯一ID`）
3. 系统给子 Agent 注入专门的系统提示，告诉它："你是一个子 Agent，你的唯一任务是……"
4. **立即返回**——主 Agent 不需要等，可以继续做其他事

**阶段二：执行**
- 子 Agent 在自己的独立会话中工作
- 使用受限的工具集（后面详述）
- 不能和用户直接交互

**阶段三：完成检测**
- 系统通过内部事件监听器检测到子 Agent 完成工作（或超时、出错）
- 记录完成状态和统计数据（耗时、消耗 token 数、成本等）

**阶段四：播报（Announce）**
- 系统让子 Agent 对自己的工作做一个总结
- 然后把这个总结发送给主 Agent 所在的频道
- 主 Agent 收到后，用自己的风格把结果呈现给用户

**阶段五：清理**
- 子 Agent 的会话根据策略处理：
  - `keep`：保留一段时间后自动归档（默认 60 分钟后）
  - `delete`：播报完成后立即删除

### 3.3 子 Agent 可以控制的参数

在派遣子 Agent 时，主 Agent 可以指定：

| 参数 | 作用 | 默认值 |
|------|------|-------|
| task | 任务描述（必填） | — |
| label | 给这个子任务起个名字 | 空 |
| agentId | 让哪个 Agent 身份去执行（可以跨 Agent） | 和主 Agent 相同 |
| model | 用哪个模型 | 继承主 Agent |
| thinking | 思考模式 | 继承主 Agent |
| runTimeoutSeconds | 超时时间 | 0（不限时） |
| cleanup | 完成后是保留还是删除会话 | keep |

### 3.4 子 Agent 的隔离性

子 Agent 的隔离非常彻底：

| 方面 | 隔离方式 |
|------|---------|
| **会话** | 全新独立会话，有唯一 ID |
| **工具** | 默认禁用会话管理工具、系统管理工具等 |
| **上下文** | 只能看到 AGENTS.md 和 TOOLS.md，看不到用户档案等 |
| **通信** | 不能和用户直接对话，不能派遣自己的子 Agent |
| **认证** | 继承主 Agent 的认证配置，但会话完全独立 |

### 3.5 不能套娃

一个很重要的限制：**子 Agent 不能再派遣子 Agent**。也就是说，"分身"不能再"分身"，只允许一层深度。这是为了防止无限递归导致资源失控。

## 四、安全与授权：谁能和谁说话

### 4.1 默认全部关闭

OpenClaw 的 Agent 间通信**默认是完全关闭的**。即使你配置了多个 Agent，它们之间也无法互相发消息或派遣子 Agent（除非是同一个 Agent 内部的操作）。

要开启通信，必须显式配置。

### 4.2 Agent-to-Agent 策略（适用于 sessions_send）

直接对话的授权分为两层：

**第一层：总开关**

整个系统有一个总开关 `tools.agentToAgent.enabled`，必须设置为 `true` 才能让 Agent 之间直接对话。如果关闭，所有跨 Agent 的 `sessions_send` 都会被拒绝。

注意：同一个 Agent 内部的会话间通信不受这个开关影响，始终允许。

**第二层：白名单**

开启总开关后，还可以通过 `tools.agentToAgent.allow` 设置白名单，精确控制哪些 Agent 可以互相通信：

| 白名单写法 | 含义 |
|-----------|------|
| `["alice", "bob"]` | 只有 alice 和 bob 可以互相通信 |
| `["user-*"]` | 所有 ID 以 `user-` 开头的 Agent 可以互相通信 |
| `["*"]` | 所有 Agent 都可以互相通信 |
| 空列表 `[]` | 不限制（等同于 `["*"]`） |

**重要细节**：白名单是**双向检查**的——发起方和接收方都必须匹配白名单中的模式，通信才会被允许。

### 4.3 子 Agent 跨 Agent 派遣授权（适用于 sessions_spawn）

子 Agent 的派遣有自己独立的授权体系：

- 默认情况下，一个 Agent 只能以自己的身份派遣子 Agent
- 如果想以其他 Agent 的身份派遣，需要在配置中设置 `subagents.allowAgents`

| 配置写法 | 含义 |
|---------|------|
| `["researcher", "analyst"]` | 只能派遣 researcher 和 analyst |
| `["*"]` | 可以派遣任何 Agent |
| 不设置 | 只能以自己的身份派遣 |

### 4.4 子 Agent 的工具限制

子 Agent 默认被禁用了一批工具，以防止它做出"越权"操作：

**默认禁用的工具：**
- `sessions_list` / `sessions_history` / `sessions_send` / `sessions_spawn`（不能操作其他会话）
- `gateway`（不能操作网关）
- `agents_list`（不能查看 Agent 列表）
- `session_status`（不能查看会话状态）
- `cron`（不能设置定时任务）
- `memory_search` / `memory_get`（不能访问记忆系统）

**默认允许的工具：**
- 文件读写、代码执行等编程类工具
- 网页搜索、网页抓取等信息获取工具
- 频道消息发送等通信工具

这些限制可以通过配置自定义，但默认策略已经足够安全。

## 五、并发与队列：多个任务同时进行

### 5.1 执行通道（Lane）

OpenClaw 用"通道"的概念来管理不同类型任务的并发：

| 通道 | 用途 | 说明 |
|------|------|------|
| 子 Agent 通道 | `sessions_spawn` 派遣的任务 | 有并发上限（默认 8 个） |
| 嵌套通道 | `sessions_send` 的对话和 Ping-Pong | 独立管理 |

当子 Agent 的并发数达到上限时，新的派遣任务会进入队列等待，直到有空闲位置。

### 5.2 播报队列

如果主 Agent 正在忙（比如正在和用户对话），子 Agent 的播报消息不会立即打断，而是进入一个播报队列，等主 Agent 空闲时再投递。

## 六、事件系统：内部协调的基础

在这两套沟通机制的底层，有一个**事件系统**在支撑。

### 6.1 事件类型

| 事件流 | 包含的事件 |
|--------|-----------|
| lifecycle | 运行开始（start）、运行结束（end）、运行出错（error） |
| tool | 工具调用事件 |
| assistant | AI 回复事件 |
| error | 错误事件 |

### 6.2 事件的作用

最典型的用途是**子 Agent 完成检测**：

1. 子 Agent 被派遣后，系统注册一个事件监听器
2. 监听器关注 `lifecycle` 事件流中的 `end` 和 `error` 事件
3. 当检测到子 Agent 完成时，自动触发播报流程

这个事件系统是进程内的（不是分布式消息队列），所以如果网关重启，正在进行中的事件监听会丢失。不过 OpenClaw 有一个**持久化恢复机制**：子 Agent 的注册信息会写入磁盘，网关重启后会自动恢复未完成的子 Agent 状态。

## 七、完整的协作模式示例

### 模式一：任务委派

最常见的模式。主 Agent 把复杂任务拆解，派遣多个子 Agent 并行处理。

```
用户: "帮我分析这三个竞品"

主 Agent 的处理：
├── 派遣子 Agent 1 → 研究竞品 A
├── 派遣子 Agent 2 → 研究竞品 B（同时进行）
├── 派遣子 Agent 3 → 研究竞品 C（同时进行）
│
│  ← 子 Agent 1 完成，播报结果
│  ← 子 Agent 2 完成，播报结果
│  ← 子 Agent 3 完成，播报结果
│
└── 主 Agent 汇总三份结果，回复用户
```

### 模式二：专家咨询

主 Agent 遇到专业问题，通过直接对话向专家 Agent 请教。

```
用户: "帮我写一段 SQL 然后优化性能"

主 Agent 的处理：
├── 自己先写了一段 SQL
├── 通过 sessions_send 发给 "DBA Agent"
│   ├── DBA Agent 回复：建议加索引（第1轮）
│   ├── 主 Agent 追问：哪些字段加索引？（第2轮）
│   ├── DBA Agent 回复：具体建议（第3轮）
│   └── 主 Agent 回复 REPLY_SKIP（结束对话）
│
└── 主 Agent 把 SQL + 优化建议一起回复用户
```

### 模式三：流水线处理

多个 Agent 按顺序处理，像工厂流水线一样。

```
用户: "帮我生成一份市场报告"

处理流程：
Agent A（数据收集）
  → 通过 sessions_send 将数据发给 Agent B
Agent B（数据分析）
  → 通过 sessions_send 将分析发给 Agent C
Agent C（报告撰写）
  → 生成最终报告，通知用户
```

### 模式四：路由分发

一个"调度 Agent"根据问题类型，把消息转发给不同的专业 Agent。

```
用户: "我的订单出了问题"

调度 Agent 的处理：
├── 判断：这是一个订单问题
├── 通过 sessions_send 转发给 "订单 Agent"
├── 订单 Agent 处理并回复
└── 调度 Agent 把回复转发给用户
```

## 八、两种机制的对比

| 对比项 | sessions_send（直接对话） | sessions_spawn（派遣子代） |
|--------|------------------------|--------------------------|
| **通信方式** | Agent ↔ Agent 双向对话 | 主 Agent → 子 Agent 单向派遣 |
| **是否阻塞** | 可选（等回复 or 发了就走） | 永远不阻塞（立即返回） |
| **会话关系** | 两个独立的已有会话 | 自动创建全新的临时会话 |
| **对话深度** | 支持多轮 Ping-Pong（最多5轮） | 子 Agent 只处理一个任务 |
| **结果获取** | 直接拿到回复 | 通过播报机制异步获取 |
| **可否嵌套** | 无限制 | 不能嵌套（子不能再派子） |
| **授权方式** | agentToAgent.enabled + allow | subagents.allowAgents |
| **适用场景** | 协商、咨询、交换信息 | 委派具体任务、并行处理 |
| **默认状态** | 关闭 | 同 Agent 可用，跨 Agent 需授权 |

## 九、没有"转接"：一个重要的缺失

值得特别指出的是，OpenClaw **没有传统意义上的"会话转接"（Handoff）机制**。也就是说：

- 不能把一个正在进行的用户对话从 Agent A 转移到 Agent B
- 不能把对话历史一起搬过去
- 不能做到"无缝切换"，让用户感觉还在和同一个对象聊天

Agent 之间的沟通本质上都是**新开一个独立的通信通道**，而不是"接管"已有对话。

如果业务上需要类似"转接"的效果，可以通过以下方式模拟：
1. Agent A 通过 `sessions_send` 把对话摘要发给 Agent B
2. Agent B 基于摘要继续处理
3. 通过路由绑定规则，把后续消息定向到 Agent B

但这本质上是"断开-重建"，不是真正的无缝转接。

## 十、总结

OpenClaw 的多 Agent 沟通机制可以用一句话概括：**默认隔离，按需连接，有限协作**。

- **默认隔离**：所有跨 Agent 通信默认关闭，必须显式开启
- **按需连接**：通过白名单精确控制谁能和谁说话
- **有限协作**：支持直接对话和任务派遣，但不支持会话转接

这种设计的好处是**安全性高、边界清晰**——每个 Agent 的职责范围是明确的，不会出现"越权操作"的问题。但同时也意味着**深度协作需要额外的设计**——如果你需要多个 Agent 紧密配合，就需要在配置上和流程设计上多花心思。

对于想要构建多 Agent 产品的开发者来说，建议的做法是：
1. **先把每个 Agent 的职责划分清楚**
2. **只开启必要的通信通道**
3. **用子 Agent 处理可并行的任务**
4. **用直接对话处理需要协商的场景**
5. **在应用层处理需要"转接"的场景**
