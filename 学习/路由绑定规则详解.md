# 路由绑定规则（Bindings）详解

> 核心问题：当一条消息从外部（WhatsApp、Telegram、你的前端页面等）进入 OpenClaw 时，系统怎么知道该交给哪个 Agent 处理？答案就是路由绑定规则（Bindings）。

---

## 一、什么是绑定规则

绑定规则就是一张"分发表"，告诉系统：

> "满足某个条件的消息，交给某个 Agent 处理。"

每一条绑定规则包含两部分：

| 部分 | 含义 | 举例 |
|------|------|------|
| **agentId** | 交给谁 | "user-001" |
| **match** | 什么条件下触发 | "来自 my-chat 渠道的 user-001 的私聊消息" |

用快递分拣来类比：

> 绑定规则就像快递分拣中心的标签规则。
> 写着"北京朝阳区"的包裹 → 放到朝阳区的货架。
> 写着"上海浦东"的包裹 → 放到浦东的货架。
> 没有标签的包裹 → 放到默认货架。
>
> "标签内容"就是 match 条件，"货架"就是 Agent。

---

## 二、match 条件可以匹配哪些维度

一条绑定规则的 match 部分可以包含以下维度（不是所有维度都必须填）：

### 2.1 渠道（channel）

**必填。** 每条绑定规则都必须指定一个渠道。

渠道就是消息的来源平台。比如 `"whatsapp"`、`"telegram"`、`"slack"`、`"discord"`，或者你自己开发的前端渠道 `"my-chat"`。

```
match: { channel: "my-chat" }

含义：所有来自 my-chat 渠道的消息
```

### 2.2 账号（accountId）

**可选。** 用于区分同一个渠道的不同账号实例。

比如你在 WhatsApp 上有两个号码（一个个人号、一个工作号），就需要用 accountId 来区分：

```
match: { channel: "whatsapp", accountId: "personal" }
含义：来自个人号的 WhatsApp 消息

match: { channel: "whatsapp", accountId: "business" }
含义：来自工作号的 WhatsApp 消息
```

特殊值：
- 不填 accountId → 只匹配默认账号（`"default"`）
- 填 `"*"` → 匹配该渠道下的**所有**账号（通配符）

### 2.3 对端（peer）

**可选。** 用于精确匹配某个特定的聊天对象或群组。

peer 由两个字段组成：

| 字段 | 含义 | 可选值 |
|------|------|-------|
| `kind` | 聊天类型 | `"dm"`（私聊）、`"group"`（群组）、`"channel"`（频道） |
| `id` | 对端标识 | 用户 ID、群组 ID、频道 ID 等 |

```
match: { channel: "whatsapp", peer: { kind: "dm", id: "+8613800000001" } }
含义：来自这个手机号的 WhatsApp 私聊消息

match: { channel: "whatsapp", peer: { kind: "group", id: "120363406150318674@g.us" } }
含义：来自这个 WhatsApp 群的消息

match: { channel: "my-chat", peer: { kind: "dm", id: "user-001" } }
含义：来自你前端页面上 user-001 的私聊消息
```

### 2.4 服务器（guildId）

**可选。** 专用于 Discord。

Discord 的组织层级是"服务器（Guild）→ 频道"。guildId 可以让你按服务器级别路由：

```
match: { channel: "discord", guildId: "123456789012345678" }
含义：这个 Discord 服务器里的所有消息
```

### 2.5 工作区（teamId）

**可选。** 专用于 Slack。

Slack 的组织层级是"工作区（Team/Workspace）→ 频道"。teamId 可以让你按工作区级别路由：

```
match: { channel: "slack", teamId: "T01234ABCDE" }
含义：这个 Slack 工作区里的所有消息
```

### 2.6 维度总结

```
match 条件的完整结构：

match: {
    channel:    "渠道名",         ← 必填
    accountId:  "账号标识",       ← 可选
    peer: {                       ← 可选
        kind:   "dm/group/channel",
        id:     "对端标识"
    },
    guildId:    "Discord 服务器", ← 可选，Discord 专用
    teamId:     "Slack 工作区"    ← 可选，Slack 专用
}
```

填的维度越多，规则就越精确。

## 三、匹配优先级：越具体的规则越优先

当一条消息进来时，可能同时满足多条绑定规则。系统的处理方式是：**按优先级逐层匹配，第一个命中的规则生效。**

优先级从高到低：

```
第 1 优先级：peer 匹配（精确到某个人或某个群）
      │
      │  如果没命中 ↓
      │
第 2 优先级：父级 peer 匹配（线程继承父消息的路由）
      │
      │  如果没命中 ↓
      │
第 3 优先级：guildId 匹配（Discord 服务器级别）
      │
      │  如果没命中 ↓
      │
第 4 优先级：teamId 匹配（Slack 工作区级别）
      │
      │  如果没命中 ↓
      │
第 5 优先级：accountId 匹配（具体账号，不带 peer/guild/team）
      │
      │  如果没命中 ↓
      │
第 6 优先级：channel 通配匹配（accountId="*"，不带 peer/guild/team）
      │
      │  如果没命中 ↓
      │
第 7 优先级：默认 Agent（兜底）
```

### 为什么要有优先级

这个设计让你可以用"一般规则 + 特殊例外"的方式来管理路由。比如：

```
规则 1：channel="whatsapp"                          → Agent "chat"
规则 2：channel="whatsapp", peer={dm, "+861380..."}  → Agent "vip"
```

大部分 WhatsApp 消息走规则 1，交给普通的 chat Agent。但特定用户的私聊走规则 2，交给 vip Agent。**不需要为每个普通用户都写一条规则**——没被精确匹配到的消息自然会掉到更宽泛的规则里。

### 匹配过程图解

用一个具体例子走一遍：

```
收到一条消息：
  channel = "my-chat"
  accountId = "default"
  peer = { kind: "dm", id: "user-007" }

系统开始匹配：

  步骤 1：预过滤
    先把所有绑定规则中，channel 不是 "my-chat" 的过滤掉
    再把 accountId 不匹配的过滤掉
    剩下的才进入优先级匹配

  步骤 2：找 peer 匹配
    有没有规则的 peer.id == "user-007"？
    ├── 有 → 命中！用这条规则的 agentId，结束
    └── 没有 → 继续

  步骤 3：找父级 peer 匹配（仅线程消息）
    这条消息是线程回复吗？
    ├── 是 → 用父消息的 peer 再匹配一次
    └── 不是 → 跳过

  步骤 4：找 guildId 匹配
    这条消息带 guildId 吗？
    └── 不带（不是 Discord）→ 跳过

  步骤 5：找 teamId 匹配
    这条消息带 teamId 吗？
    └── 不带（不是 Slack）→ 跳过

  步骤 6：找 accountId 匹配
    有没有规则只指定了 channel + accountId（不带 peer/guild/team）？
    ├── 有 → 命中！用这条规则的 agentId，结束
    └── 没有 → 继续

  步骤 7：找 channel 通配匹配
    有没有规则指定了 accountId="*"（所有账号）？
    ├── 有 → 命中！用这条规则的 agentId，结束
    └── 没有 → 继续

  步骤 8：兜底
    用默认 Agent（配置中标记了 default: true 的，或者 agents.list 的第一个）
```

## 四、在多用户方案中怎么用

回到我们的"一个用户一个 Agent"方案，绑定规则长这样：

```
用户 user-001 注册时，添加绑定：
  { agentId: "user-001", match: { channel: "my-chat", peer: { kind: "dm", id: "user-001" } } }

用户 user-002 注册时，添加绑定：
  { agentId: "user-002", match: { channel: "my-chat", peer: { kind: "dm", id: "user-002" } } }

用户 user-003 注册时，添加绑定：
  { agentId: "user-003", match: { channel: "my-chat", peer: { kind: "dm", id: "user-003" } } }
```

当 user-001 发消息时：
1. 预过滤：channel="my-chat" ✅
2. peer 匹配：peer.id="user-001" → 命中！→ 交给 Agent "user-001"

当一个未注册的用户发消息时：
1. 预过滤：channel="my-chat" ✅
2. peer 匹配：没有任何规则的 peer.id 等于这个用户 → 未命中
3. 一路跳到兜底 → 交给默认 Agent

你可以利用这个兜底机制来处理未注册用户——比如让默认 Agent 回复"请先注册"。

## 五、绑定规则的冲突处理

### 什么是冲突

如果两条绑定规则的 match 条件完全相同，但指向不同的 Agent，这就是冲突：

```
规则 A：{ agentId: "agent-a", match: { channel: "my-chat", peer: { kind: "dm", id: "user-001" } } }
规则 B：{ agentId: "agent-b", match: { channel: "my-chat", peer: { kind: "dm", id: "user-001" } } }

冲突！同一个用户的消息应该交给 agent-a 还是 agent-b？
```

### 系统怎么处理

OpenClaw 在添加绑定规则时有冲突检测：

```
添加一条新绑定时：

  这条规则的 match 条件是否已存在？
      │
      ├── 不存在 → 正常添加
      │
      └── 存在 → 已有规则指向的是同一个 Agent 吗？
              │
              ├── 是 → 跳过（不重复添加）
              │
              └── 否 → 报告冲突，不添加
```

冲突规则的唯一标识是由以下字段组合而成的：

```
冲突判定键 = channel + accountId + peer.kind + peer.id + guildId + teamId
```

只要这个组合完全相同，就视为同一条规则。

## 六、绑定规则与 Session Key 的关系

绑定规则不仅决定"消息交给谁"，还决定了**会话的唯一标识（Session Key）怎么构建**。

当一条规则命中后，系统会根据消息的上下文信息构建 Session Key：

```
匹配结果 → 确定 agentId
         → 结合 channel、accountId、peer 信息
         → 构建 Session Key

Session Key 的格式取决于聊天类型和 DM Scope 设置：

  私聊（DM）：
    dmScope="main"                    → agent:{agentId}:main
    dmScope="per-peer"                → agent:{agentId}:dm:{peerId}
    dmScope="per-channel-peer"        → agent:{agentId}:{channel}:dm:{peerId}
    dmScope="per-account-channel-peer"→ agent:{agentId}:{channel}:{accountId}:dm:{peerId}

  群聊（Group）：
    → agent:{agentId}:{channel}:group:{groupId}

  频道（Channel）：
    → agent:{agentId}:{channel}:channel:{channelId}
```

### dmScope 是什么

dmScope 控制私聊消息的"会话合并粒度"：

| dmScope 值 | 含义 | 效果 |
|-----------|------|------|
| `"main"` | 所有私聊合并为一个会话 | 不管跟谁聊，都是同一个 Session（默认值） |
| `"per-peer"` | 按对方区分 | 跟张三聊是一个 Session，跟李四聊是另一个 |
| `"per-channel-peer"` | 按渠道+对方区分 | WhatsApp 的张三和 Telegram 的张三是不同 Session |
| `"per-account-channel-peer"` | 按账号+渠道+对方区分 | 最细粒度 |

**在你的多用户方案中，建议用 `"per-peer"` 或更细的粒度。** 因为 `"main"` 会把所有用户的私聊合并到一个 Session 里，这在多用户场景下完全不可接受。

### 为什么 Session Key 重要

Session Key 决定了：
- 聊天记录存在哪个文件里
- 沙箱容器怎么分配（scope="session" 时）
- 消息队列怎么排队（同 Session 串行处理，不同 Session 可以并行）

所以绑定规则 → Session Key → 整个隔离体系。绑定规则是隔离链条的起点。

## 七、线程继承

一个细节功能：当消息是一个线程（Thread）里的回复时，如果这条消息本身的 peer 没有命中任何绑定规则，系统会尝试用**父消息的 peer** 再匹配一次。

```
场景：
  Slack 频道里，用户 A 发了一条消息，Agent X 回复了
  用户 B 在这条回复下面开了一个线程讨论

匹配过程：
  用户 B 的线程消息 → peer 匹配 → 没有针对用户 B 的规则
                   → 父级 peer 匹配 → 父消息的发送者是用户 A → 命中用户 A 的规则
                   → 这条线程消息也交给 Agent X
```

这保证了一个线程里的所有消息都路由到同一个 Agent，不会因为参与者不同而被拆散到不同的 Agent。

## 八、绑定规则的管理方式

### 通过 CLI 命令

```
添加 Agent 时自动创建绑定：
  openclaw agents add work --bind whatsapp:business

查看所有绑定：
  openclaw agents list --bindings

手动编辑配置文件中的 bindings 数组
```

### 通过配置文件

直接编辑 `openclaw.json` 中的 `bindings` 数组：

```
配置文件中的结构：

{
  bindings: [
    { agentId: "home", match: { channel: "whatsapp", accountId: "personal" } },
    { agentId: "work", match: { channel: "whatsapp", accountId: "business" } },
    { agentId: "vip",  match: { channel: "whatsapp", peer: { kind: "dm", id: "+861380..." } } },
  ]
}
```

### 通过你的后端（多用户方案）

在前面讨论的方案中，你的后端在用户注册时会通过 Gateway RPC（或直接操作配置文件/数据库）来添加绑定规则。

## 九、常见绑定模式

### 模式一：一个渠道一个 Agent（最简单）

```
所有 WhatsApp 消息 → Agent "chat"
所有 Telegram 消息 → Agent "deep"

bindings:
  { agentId: "chat", match: { channel: "whatsapp" } }
  { agentId: "deep", match: { channel: "telegram" } }
```

### 模式二：同渠道多账号各一个 Agent

```
个人 WhatsApp 号 → Agent "home"
工作 WhatsApp 号 → Agent "work"

bindings:
  { agentId: "home", match: { channel: "whatsapp", accountId: "personal" } }
  { agentId: "work", match: { channel: "whatsapp", accountId: "business" } }
```

### 模式三：一般规则 + 特殊例外

```
大部分 WhatsApp → Agent "chat"（快速模型）
老板的私聊     → Agent "opus"（高能模型）

bindings:
  { agentId: "opus", match: { channel: "whatsapp", peer: { kind: "dm", id: "+861380..." } } }
  { agentId: "chat", match: { channel: "whatsapp" } }

注意：精确规则（peer）要放在前面，但实际上顺序不影响结果，
因为系统按优先级（peer > account > channel）匹配，不是按数组顺序。
```

### 模式四：多用户产品（每个用户一条绑定）

```
bindings:
  { agentId: "user-001", match: { channel: "my-chat", peer: { kind: "dm", id: "user-001" } } }
  { agentId: "user-002", match: { channel: "my-chat", peer: { kind: "dm", id: "user-002" } } }
  { agentId: "user-003", match: { channel: "my-chat", peer: { kind: "dm", id: "user-003" } } }
  ...
  { agentId: "main",     match: { channel: "my-chat" } }  ← 兜底：未注册用户
```

### 模式五：群组绑定

```
家庭群 → Agent "family"（受限权限）

bindings:
  { agentId: "family", match: { channel: "whatsapp", peer: { kind: "group", id: "120363...@g.us" } } }
```

## 十、总结

绑定规则的设计哲学是**声明式 + 确定性**：

- **声明式**：你不需要写逻辑代码来做路由判断，只需要声明"什么条件对应什么 Agent"
- **确定性**：同样的消息，无论经过多少次路由解析，结果总是一样的。不存在随机性或 AI 自主判断

这跟很多 Multi-Agent 框架的做法不同——有些框架让一个"管理 Agent"来决定消息交给谁。OpenClaw 的做法更像网络路由表：规则写好了，数据包进来就按规则转发，不需要"智能判断"。

好处是可靠、可审计、可预测。代价是灵活度有限——如果你真的需要"根据消息内容动态选择 Agent"，需要在你的渠道插件层自己实现判断逻辑，然后通过设置消息上下文中的 peer 信息来影响路由结果。
