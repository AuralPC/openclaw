# OpenClaw Sandbox 沙箱系统分析（小白友好版）

> 这份文档用通俗易懂的语言解释 OpenClaw 的沙箱系统，重点关注"是什么"、"为什么"和"怎么工作"。

## 🤔 什么是沙箱？

### 生活中的类比

想象一下：
- 🏖️ **沙滩上的沙箱**：小孩在沙箱里玩沙子，无论怎么折腾，都不会影响到沙箱外面的花园
- 🧪 **实验室的防护罩**：科学家在防护罩内做危险实验，即使出错也不会伤害到外面的人
- 🎮 **游戏的试玩模式**：你可以随便尝试，不会影响到你的正式存档

**计算机中的沙箱**就是类似的概念：
- 创建一个"隔离的小房间"
- 在里面运行不完全信任的程序
- 即使程序出问题，也不会影响到外面的系统

## 🎯 为什么需要沙箱？

### OpenClaw 的使用场景

OpenClaw 是一个 AI 助手，它可以：
- 执行命令（比如删除文件、安装软件）
- 运行用户提供的脚本
- 访问网络和文件系统
- 处理来自各种渠道的请求

**潜在风险**：
1. **AI 可能被误导**：用户可能无意中让 AI 执行危险命令
2. **恶意输入**：如果有人试图攻击系统，可能会构造特殊的输入
3. **Bug 或错误**：程序可能有 Bug，导致意外删除重要文件
4. **权限失控**：给 AI 完全的系统权限太危险了

### 沙箱的保护作用

```
没有沙箱的情况：
用户 → AI → 直接在你的电脑上执行 → 💥 可能造成损害

有沙箱的情况：
用户 → AI → 在隔离的容器中执行 → ✅ 即使出错也是隔离的
```

## 🏗️ OpenClaw 沙箱的工作原理

### 整体架构（用房子做比喻）

想象 OpenClaw 是一个大房子：

```
┌─────────────────────────────────────────┐
│         主房子（你的电脑）                 │
│  ┌───────────────────────────────┐      │
│  │  OpenClaw Gateway             │      │
│  │  (总管家，永远在主房子里)       │      │
│  └───────────────────────────────┘      │
│                │                         │
│                │ 决定在哪里执行命令         │
│                ▼                         │
│       ┌────────┴────────┐               │
│       │                 │               │
│  【选项1】          【选项2】              │
│   在主房子           在隔离小屋            │
│   直接执行           (Docker 容器)        │
│   🏠                🧱                   │
│                                         │
│  ┌─────────────────────────────────┐   │
│  │  隔离小屋（沙箱容器）             │   │
│  │                                 │   │
│  │  • 独立的房间                    │   │
│  │  • 只有基本工具                  │   │
│  │  • 不能随意出入                  │   │
│  │  • 资源有限制                    │   │
│  │                                 │   │
│  │  在这里运行不太信任的命令         │   │
│  └─────────────────────────────────┘   │
└─────────────────────────────────────────┘
```

### 三种运行模式

OpenClaw 的沙箱有三种工作模式：

#### 模式 1：关闭（"off"）- 默认模式
```
完全信任模式
所有命令都在你的电脑上直接运行
就像你自己在终端输入命令一样
⚡ 快速，但风险较高
```

**适用场景**：
- 个人使用，完全信任 AI
- 本地开发，需要完整权限

#### 模式 2：非主会话模式（"non-main"）
```
半信任模式
- 你直接跟 AI 对话：在主房子运行（信任）
- 通过 Telegram/Discord 等渠道：在隔离小屋运行（不完全信任）
```

**适用场景**：
- 你自己使用时要速度
- 其他人或其他渠道使用时要安全

#### 模式 3：始终开启（"on"）
```
最安全模式
所有命令都在隔离小屋运行
即使你自己的命令也被隔离
🛡️ 最安全，但稍慢
```

**适用场景**：
- 生产环境
- 多用户共享
- 处理敏感数据

### 会话作用域（容器的复用策略）

沙箱容器就像酒店房间，有三种预订方式：

#### 作用域 1：per-session（每次会话一个房间）
```
每次新对话 → 开一个新房间
优点：完全隔离
缺点：慢（每次都要准备房间）
```

就像每个客人都要住全新的房间。

#### 作用域 2：per-agent（每个 Agent 一个房间）
```
同一个 AI 助手 → 共用一个房间
不同的 AI 助手 → 各用各的房间
优点：平衡速度和隔离
缺点：同一 Agent 的不同会话共享环境
```

就像一个客人长期包一个房间，每次来都住这间。

#### 作用域 3：shared（所有人共享一个房间）
```
所有会话 → 共用一个房间
优点：最快（房间一直准备好）
缺点：隔离性最差
```

就像青年旅社的多人间。

## 🔒 沙箱的安全机制

### 多层防护体系

想象沙箱是一个高安全性的银行金库：

```
┌─────────────────────────────────────┐
│ 第一层：门卫（工具策略）              │
│ 检查：这个工具允许执行吗？             │
│ ├─ 允许列表（白名单）                 │
│ └─ 拒绝列表（黑名单）                 │
└─────────────────────────────────────┘
              ↓ 通过
┌─────────────────────────────────────┐
│ 第二层：决策（沙箱模式）              │
│ 判断：在哪里执行？                    │
│ ├─ 主房子（直接执行）                 │
│ └─ 隔离小屋（Docker 容器）            │
└─────────────────────────────────────┘
              ↓ 进入沙箱
┌─────────────────────────────────────┐
│ 第三层：物理隔离（Docker 容器）        │
│ 限制：文件、网络、资源                │
└─────────────────────────────────────┘
```

### 第一层：工具策略（门卫检查）

**工作原理**：
- 维护两个列表：允许列表和拒绝列表
- 拒绝列表优先（先检查是否被禁止）
- 允许列表兜底（检查是否被允许）

**类比**：
```
就像夜店门口的保安：
1. 先看黑名单：这个人是不是被禁止入内的？
2. 再看白名单：这个人是不是 VIP 可以进入？
3. 都不是的话，看默认策略
```

**默认允许的工具**：
- `exec` - 执行命令
- `read`, `write`, `edit` - 文件操作
- `process` - 进程管理
- `image` - 图片处理

**默认拒绝的工具**：
- `browser` - 浏览器操作（需要特殊权限）
- `cron` - 定时任务（可能长期运行）
- `gateway` - 网关操作（太核心了）
- 渠道相关工具 - 发送消息（防止滥用）

### 第二层：Docker 容器隔离

Docker 容器就像一个加固的保险箱：

#### 隔离 1：文件系统隔离
```
┌─────────────────────────────────────┐
│ 你的电脑（真实文件系统）              │
│ ├─ /home/                           │
│ ├─ /etc/                            │
│ └─ /usr/                            │
└─────────────────────────────────────┘
        │（隔离墙）
        ▼
┌─────────────────────────────────────┐
│ 沙箱容器（看不到你的文件）            │
│ ├─ /workspace/ （临时工作区）        │
│ ├─ /tmp/ （临时文件）                │
│ └─ 其他位置都是只读的！               │
└─────────────────────────────────────┘
```

**保护效果**：
- 沙箱内的程序**看不到**你的个人文件
- 无法修改系统文件（只读根文件系统）
- 只能在 `/workspace` 和 `/tmp` 工作

#### 隔离 2：网络隔离
```
默认配置：没有网络！

你的电脑 ←→ 互联网  ✅ 正常上网
     ↓
沙箱容器 ←✗→ 互联网  ❌ 完全断网
```

**为什么要断网？**
- 防止恶意程序向外发送数据
- 防止下载恶意软件
- 限制攻击面

**什么时候需要网络？**
- 安装软件包（需要临时开启）
- 访问 API（需要配置允许）

#### 隔离 3：权限隔离
```
Linux 系统有很多"超能力"（capabilities）：
- CAP_NET_ADMIN：控制网络
- CAP_SYS_ADMIN：管理系统
- CAP_CHOWN：改变文件所有者
- ... 等等

沙箱容器：把所有超能力都拿掉！ 🚫
```

**效果**：即使有人攻破沙箱，也无法：
- 监听网络流量
- 修改系统配置
- 提权到 root
- 访问硬件设备

#### 隔离 4：资源限制
```
就像给房间设置规则：
- 内存：最多用 512MB（可配置）
- CPU：最多用 1 个核心（可配置）
- 进程数：最多 100 个（可配置）
- 磁盘空间：限制在特定目录
```

**防止的问题**：
- 内存炸弹（无限分配内存）
- CPU 死循环（占满 CPU）
- 进程炸弹（无限创建进程）

### 第三层：工作区访问模式

沙箱可以用三种方式访问你的工作文件：

#### 模式 1：完全隔离（"none"）- 最安全
```
沙箱的文件                  你的文件
┌──────────┐               ┌──────────┐
│ /workspace│ ←✗→           │  真实目录 │
│（独立的）  │   完全隔离     │          │
└──────────┘               └──────────┘

优点：最安全，沙箱完全独立
缺点：无法访问你的项目文件
```

#### 模式 2：只读访问（"ro"）- 平衡
```
沙箱的文件                  你的文件
┌──────────┐               ┌──────────┐
│ /agent   │ ←──只读───     │  真实目录 │
│（只读）    │   不能改       │          │
└──────────┘               └──────────┘

优点：可以读取项目文件，但不能修改
缺点：无法写入结果
```

#### 模式 3：读写访问（"rw"）- 最方便
```
沙箱的文件                  你的文件
┌──────────┐               ┌──────────┐
│/workspace │ ←──读写───    │  真实目录 │
│（映射）    │   双向同步     │          │
└──────────┘               └──────────┘

优点：完全访问，就像本地运行
缺点：安全性降低（可能误删文件）
```

## 🛠️ 沙箱内的工具和环境

### 默认提供的工具

沙箱容器就像一个"精简版 Linux 系统"，预装了常用工具：

```
📦 基础工具箱包含：
- bash       → 命令行 Shell
- python3    → Python 解释器
- git        → 版本控制
- curl       → 网络请求
- jq         → JSON 处理
- ripgrep    → 文本搜索
- ca-certificates → SSL 证书（安全连接）
```

### 不包含的工具（需要自己安装）

```
❌ 默认没有：
- Node.js
- Ruby
- Java
- Go
- ...其他语言运行时
```

### 如何添加自己需要的工具？

有两种方式：

#### 方式 1：安装时运行命令（适合简单场景）
```
配置一个"首次启动脚本"
第一次创建容器时，自动运行这个脚本
例如：安装 Node.js
```

**缺点**：
- 每次创建新容器都要重新安装
- 需要开启网络（破坏了默认隔离）
- 需要关闭只读根文件系统

#### 方式 2：自定义镜像（适合复杂场景）
```
自己制作一个 Docker 镜像
把所有需要的工具都装好
就像装修好房子再租出去
```

**优点**：
- 一次制作，到处使用
- 启动速度快
- 保持安全配置

## 🔄 容器的生命周期管理

### 容器何时创建？

```
用户请求 → 需要沙箱执行
   ↓
检查：容器存在吗？
   ├─ 存在 → 复用（快速）
   └─ 不存在 → 创建（稍慢）
```

### 容器何时被删除？

OpenClaw 有一个"清理工"系统，定期清理：

```
每 5 分钟检查一次：
- 超过 24 小时没用的容器 → 删除
- 超过 7 天的容器（无论是否使用）→ 删除
```

**为什么要删除？**
- 节省磁盘空间
- 避免容器堆积
- 清理旧的配置

**什么时候不会删除？**
- 最近 24 小时内使用过
- 还在运行中

### 配置变更时的处理

```
情况：你改了沙箱配置（比如加了新的资源限制）
      ↓
OpenClaw 检测到配置变化（通过 hash 对比）
      ↓
判断：容器最近使用过吗？
   ├─ 5 分钟内用过 → ⚠️ 警告但继续用旧容器
   └─ 超过 5 分钟 → 删除旧容器，创建新的
```

## 🎛️ 配置和使用建议

### 配置位置

OpenClaw 的配置文件通常在：
```
~/.openclaw/config.yaml
```

### 常见配置场景

#### 场景 1：个人使用，追求速度
```yaml
agents:
  defaults:
    sandbox:
      mode: "off"  # 关闭沙箱，最快速
```

**适合**：你完全信任自己的操作

#### 场景 2：多渠道使用，主会话免沙箱
```yaml
agents:
  defaults:
    sandbox:
      mode: "non-main"        # 非主会话才沙箱
      scope: "per-agent"      # 每个 Agent 一个容器
      workspaceAccess: "ro"   # 只读访问
```

**适合**：日常对话要快，Telegram 等渠道要安全

#### 场景 3：最高安全，生产环境
```yaml
agents:
  defaults:
    sandbox:
      mode: "on"              # 全部沙箱
      scope: "per-session"    # 每次会话隔离
      workspaceAccess: "none" # 完全隔离
      docker:
        readOnlyRoot: true    # 只读根系统
        network: "none"       # 无网络
        memory: "256m"        # 限制内存
        cpus: 0.5             # 限制 CPU
```

**适合**：多用户共享，处理不信任的输入

#### 场景 4：需要特殊工具（Node.js）
```yaml
agents:
  defaults:
    sandbox:
      mode: "non-main"
      docker:
        image: "my-custom-image:latest"  # 使用自定义镜像
        # 或者使用安装命令（不推荐）
        # setupCommand: "apt-get update && apt-get install -y nodejs"
        # network: "bridge"  # 需要网络来安装
```

### 工具策略配置

```yaml
agents:
  defaults:
    sandbox:
      tools:
        allow:
          - "exec"           # 允许执行命令
          - "read"           # 允许读文件
          - "write"          # 允许写文件
          - "my_custom_*"    # 允许所有 my_custom_ 开头的工具
        deny:
          - "gateway"        # 禁止网关操作
          - "*_admin"        # 禁止所有管理员工具
```

## 🤔 常见问题解答

### Q1: 沙箱安全吗？是不是绝对安全的？

**A**: 不是绝对安全的。

沙箱提供的是"**风险降低**"而不是"**完全消除**"。

就像：
- 🏠 房子的锁能防小偷，但防不住炸药
- 🦺 安全带能降低受伤风险，但不能保证零伤亡

**OpenClaw 的立场**：
> "沙箱不是完美的安全边界，但能大幅限制文件系统和进程访问。"

**实际效果**：
- ✅ 能防止误操作删除重要文件
- ✅ 能限制资源滥用
- ✅ 能隔离大部分恶意行为
- ❌ 无法防止复杂的容器逃逸攻击
- ❌ 无法防止专业黑客的定向攻击

### Q2: 使用沙箱会不会很慢？

**A**: 有一点影响，但不大。

**第一次执行**：
- 需要创建容器：+2-5 秒
- 需要拉取镜像（仅首次）：+30-60 秒

**后续执行**：
- 容器复用：+0.1-0.5 秒
- 几乎感觉不到延迟

**优化建议**：
- 使用 `per-agent` 或 `shared` 作用域（容器复用）
- 主会话使用 `non-main` 模式（免沙箱）
- 预先构建自定义镜像（避免安装等待）

### Q3: 什么时候必须使用沙箱？

**A**: 以下场景强烈建议：

1. **多用户环境**
   - 团队共享一个 OpenClaw 实例
   - 公开的 Bot 服务

2. **处理不信任的输入**
   - 运行用户提供的脚本
   - 执行来自外部的命令

3. **生产环境**
   - 线上服务
   - 处理敏感数据

4. **实验性功能**
   - 测试新功能
   - 尝试不确定的操作

### Q4: 什么时候可以关闭沙箱？

**A**: 以下场景可以考虑：

1. **个人本地使用**
   - 你完全控制输入
   - 只有你自己使用

2. **开发调试**
   - 需要完整系统访问
   - 需要调试工具

3. **性能优先**
   - 大量快速操作
   - 延迟敏感场景

### Q5: 容器会占用很多磁盘空间吗？

**A**: 不会太多。

**基础镜像**：
- 标准镜像：约 80-100 MB
- 浏览器镜像：约 300-400 MB

**容器本身**：
- 每个容器：1-10 MB（取决于使用情况）
- 自动清理：24 小时未用的会被删除

**优化建议**：
- 配置更短的 `idleHours`（如 12 小时）
- 使用 `shared` 作用域（少开容器）
- 定期手动清理：`openclaw sandbox prune`

### Q6: 如何查看当前有哪些沙箱容器？

**A**: 使用管理命令：

```bash
# 列出所有沙箱容器
openclaw sandbox list

# 列出所有浏览器容器
openclaw sandbox list --browser

# 删除所有空闲容器
openclaw sandbox prune

# 删除特定容器
openclaw sandbox remove <container-name>
```

### Q7: 沙箱里可以访问 GPU 吗？

**A**: 默认不可以，但可以配置。

需要在配置中添加 GPU 支持：
```yaml
sandbox:
  docker:
    gpus: "all"  # 使用所有 GPU
    # 或指定特殊设备
    devices:
      - "/dev/nvidia0:/dev/nvidia0"
```

**注意**：这会降低隔离性，慎用！

### Q8: 为什么我的 Node.js 脚本在沙箱里运行失败？

**A**: 因为默认镜像没有 Node.js！

**解决方案**：

**方案 1**：使用自定义镜像（推荐）
```dockerfile
FROM debian:bookworm-slim
# ... 安装 Node.js ...
```

**方案 2**：配置安装命令
```yaml
sandbox:
  docker:
    setupCommand: "curl -fsSL https://deb.nodesource.com/setup_20.x | bash - && apt-get install -y nodejs"
    network: "bridge"
    readOnlyRoot: false
```

### Q9: 沙箱能防止 AI 删除我的文件吗？

**A**: 取决于配置！

**默认配置（`workspaceAccess: "none"`）**：
- ✅ 完全防止，沙箱看不到你的文件

**只读模式（`workspaceAccess: "ro"`）**：
- ✅ 可以读，但不能修改或删除

**读写模式（`workspaceAccess: "rw"`）**：
- ❌ 可以删除！就像直接运行一样

### Q10: 遇到 "permission denied" 错误怎么办？

**可能原因**：

1. **工具被禁止**
   - 检查 `sandbox.tools.deny` 列表
   - 将工具添加到 `allow` 列表

2. **文件系统只读**
   - 尝试写入只读区域
   - 改为写入 `/workspace` 或 `/tmp`
   - 或配置 `readOnlyRoot: false`

3. **网络被禁用**
   - 默认 `network: "none"`
   - 改为 `network: "bridge"`（降低安全性）

4. **缺少权限（capabilities）**
   - 某些操作需要特殊权限
   - 考虑是否必须在沙箱运行
   - 或配置为"elevated"工具（绕过沙箱）

## 📊 总结：沙箱的利与弊

### ✅ 优点

1. **安全性提升**
   - 隔离危险操作
   - 限制系统访问
   - 防止误操作

2. **资源控制**
   - 限制内存和 CPU
   - 防止资源滥用

3. **可恢复性**
   - 容器随时可删除重建
   - 不会污染主系统

4. **多租户支持**
   - 不同用户隔离
   - 安全共享

### ❌ 缺点

1. **性能开销**
   - 创建容器有延迟
   - Docker 本身有开销

2. **功能限制**
   - 默认无网络
   - 默认无 GUI
   - 工具受限

3. **配置复杂**
   - 需要理解 Docker
   - 需要调整配置

4. **不是绝对安全**
   - 存在逃逸可能
   - 需要正确配置
