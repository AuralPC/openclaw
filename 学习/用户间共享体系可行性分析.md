# 用户间共享体系可行性分析

> 前置背景：在《动态 Agent 与多用户产品化方案》中，我们确定了"一个用户 = 一个 Agent"的架构。每个用户拥有独立的 Workspace、Session 和沙箱，隔离非常彻底。本文讨论的是：在这套隔离架构之上，如何实现用户之间的数据共享。

---

## 一、问题的本质

"隔离"和"共享"天生矛盾。OpenClaw 的设计哲学偏向隔离——每个 Agent 就像一间独立的办公室，门锁得很严。现在我们要做的，是在不拆门的前提下，给某些办公室之间开一扇窗。

先明确一下"共享"可能涉及哪些东西：

| 共享类型 | 举例 |
|---------|------|
| 文件共享 | 用户 A 把一份报告分享给用户 B |
| 知识库共享 | 多个用户都能查询同一套参考资料 |
| 对话共享 | 用户 A 把一段有价值的 AI 对话转发给用户 B 参考 |
| 协作编辑 | 多个用户同时编辑同一个文档 |
| 消息互通 | 用户 A 的 AI 助手去问用户 B 的 AI 助手一个问题 |
| 公告广播 | 管理员给所有用户的 AI 助手推送一条通知 |

---

## 二、OpenClaw 现有的跨 Agent 能力盘点

在讨论缺什么之前，先看看已经有什么。

### 2.1 Agent 间发消息

OpenClaw 有一套 Agent-to-Agent（A2A）通信机制：

- 一个 Agent 可以通过 `sessions_send` 工具，向另一个 Agent 的某个 Session 发送一条消息
- 接收方 Agent 会像收到一条普通消息一样处理它，然后把回复返回给发送方
- 甚至支持"乒乓模式"——两个 Agent 来回对话多轮

**但是这个功能默认是关闭的**，需要在配置中显式开启，并且设置允许通信的 Agent 列表。

这个能力适合做什么？

> Agent A 问 Agent B："你那边有没有上周的会议纪要？"
> Agent B 在自己的 Workspace 里找到文件，把内容回复给 Agent A。

它本质上是"两个 AI 助手之间通电话"，不是"两个用户共享一个文件夹"。

### 2.2 读取其他 Session 的历史记录

一个 Agent 可以通过 `sessions_history` 工具，查看另一个 Session 的对话记录。这意味着：

- Agent A 理论上可以去翻 Agent B 的聊天记录
- 前提是知道目标 Session 的 Key，并且没有被权限策略挡住

### 2.3 Workspace 文件的远程读写接口

Gateway 提供了 `agents.files.get` 和 `agents.files.set` 两个 RPC 方法，可以跨 Agent 读写 Workspace 文件。

**关键限制：只能操作预定义的文件。** 系统内部有一个硬编码的白名单：

```
允许操作的文件：
  AGENTS.md / SOUL.md / TOOLS.md / IDENTITY.md
  USER.md / HEARTBEAT.md / BOOTSTRAP.md / MEMORY.md
```

任何不在这个列表里的文件名都会被直接拒绝。所以这个接口的设计初衷是"管理 Agent 的人设文件"，不是"做通用文件共享"。

### 2.4 共享技能

OpenClaw 有一个全局技能目录（`~/.openclaw/skills/`），放在这里的技能所有 Agent 都能使用。但这是"技能共享"，不是"数据共享"——它分享的是"能力"，不是"内容"。

### 2.5 能力小结

| 现有能力 | 能当共享用吗 | 限制 |
|---------|------------|------|
| Agent 间发消息 | 勉强可以（让 AI 互相传内容） | 每次消耗一轮 AI 调用，有延迟和 token 成本 |
| 读取其他 Session 历史 | 勉强可以（看别人的聊天记录） | 没有细粒度权限控制 |
| 远程读写 Workspace 文件 | 不行 | 白名单限制，只能操作人设文件 |
| 共享技能 | 不适用 | 共享的是能力，不是数据 |

**结论：OpenClaw 没有原生的用户间数据共享机制。** 现有的跨 Agent 能力是为"AI 助手之间的协作"设计的，不是为"用户之间的数据共享"设计的。

---

## 三、共享体系的实现方案

既然 OpenClaw 内部不具备通用共享能力，我们需要在上层建筑中解决。核心思路是：

> **把 OpenClaw 当作纯粹的"每用户 AI 引擎"，共享逻辑放在你自己的后端服务中。**

### 整体架构定位

```
┌────────────────────────────────────────────────────────┐
│                     你的后端服务                          │
│                                                          │
│   用户体系 ─── 谁是谁，谁能看什么                         │
│   共享体系 ─── 文件共享、知识库、协作          ← 本文重点   │
│   计费体系 ─── 用量统计、套餐限额                         │
│                                                          │
│   角色：指挥官                                            │
│   职责：管理用户关系、权限、共享规则                       │
│                                                          │
└──────────────────────┬─────────────────────────────────┘
                       │
                       │  简单接口：
                       │  - 创建/销毁 Agent
                       │  - 转发消息、接收回复
                       │  - 操作 Workspace 文件
                       │
                       ▼
┌────────────────────────────────────────────────────────┐
│                   OpenClaw Gateway                       │
│                                                          │
│   角色：执行者                                            │
│   职责：管好每个用户的 AI 对话和工具调用                   │
│   不管：用户之间什么关系、谁能看谁的数据                   │
│                                                          │
└────────────────────────────────────────────────────────┘
```

### 关键认知：Workspace 就是普通文件夹

OpenClaw 的 Workspace 没有任何特殊保护：不加密、不签名、没有自定义文件格式。它就是磁盘上一个普通的目录，里面放着普通的文本文件。

这意味着你的后端服务可以**直接操作文件系统**来实现共享，完全不需要经过 OpenClaw 的 API。

## 四、逐场景方案设计

### 场景一：文件共享（用户 A 分享文件给用户 B）

**流程：**

```
用户 A 在前端点击"分享 report.md 给用户 B"
        │
        ▼
你的后端服务
        │
        ├── 1. 权限检查：A 有没有权分享？B 有没有权接收？
        │
        ├── 2. 从 A 的 Workspace 读取文件
        │       源：~/.openclaw/workspace-user-a/report.md
        │
        ├── 3. 复制到 B 的 Workspace
        │       目标：~/.openclaw/workspace-user-b/shared/from-user-a/report.md
        │
        └── 4. 完成。B 的 Agent 下次运行时，自然能看到这个文件
```

**要点：**

- 共享逻辑完全在你的后端，OpenClaw 不感知
- B 的 Agent 以为这个文件"一直在自己的 Workspace 里"
- 你可以选择是"复制"（独立副本）还是"符号链接"（实时同步）
- 权限控制由你的后端负责，OpenClaw 不参与

### 场景二：公共知识库（所有用户都能查询的参考资料）

**方案 A：每个 Workspace 放一份副本**

```
管理员上传知识库文件
        │
        ▼
你的后端遍历所有用户的 Workspace
        │
        ├── workspace-user-001/knowledge/公司手册.md
        ├── workspace-user-002/knowledge/公司手册.md
        ├── workspace-user-003/knowledge/公司手册.md
        └── ...
```

优点：简单，每个 Agent 都能直接读取。
缺点：文件重复存储，更新时需要全量同步。

**方案 B：共享目录 + 符号链接**

```
公共知识库目录：~/.openclaw/shared-knowledge/
        │
        ├── 公司手册.md
        ├── 产品文档.md
        └── FAQ.md

每个用户的 Workspace 里放一个符号链接：
  workspace-user-001/knowledge → ~/.openclaw/shared-knowledge/
  workspace-user-002/knowledge → ~/.openclaw/shared-knowledge/
```

优点：只存一份，更新即时生效。
缺点：需要注意沙箱环境下符号链接的可见性（Docker 容器需要挂载共享目录）。

**方案 C：通过 Agent 人设文件注入**

把知识库内容写进每个 Agent 的 AGENTS.md 或通过插件钩子在 Agent 启动时注入。

优点：不需要文件操作。
缺点：知识库大了会撑爆上下文窗口。只适合小量核心参考信息。

### 场景三：对话共享（用户 A 把一段对话分享给用户 B）

**流程：**

```
用户 A 在前端选择一段对话，点击"分享"
        │
        ▼
你的后端服务
        │
        ├── 1. 读取 A 的 Session 文件
        │       源：~/.openclaw/agents/user-a/sessions/xxx.jsonl
        │
        ├── 2. 提取选中的消息片段
        │
        ├── 3. 存入你的后端数据库（共享对话表）
        │       记录：谁分享的、分享给谁、内容是什么
        │
        └── 4. 用户 B 在前端可以查看这段共享对话
```

**要点：**

- 这里不需要把对话注入 B 的 Agent 中——"查看别人分享的对话"是前端展示行为，不需要 AI 参与
- 如果 B 想让自己的 AI 参考这段对话，可以在聊天中手动粘贴，或者你把内容作为消息的一部分发给 B 的 Agent
- Session 文件是标准的 JSONL 格式，你的后端可以直接解析

### 场景四：Agent 间协作（A 的 AI 去问 B 的 AI）

**这个 OpenClaw 原生支持！**

```
配置：
  tools.agentToAgent.enabled = true
  tools.agentToAgent.allow = ["user-*"]  ← 通配符，允许所有用户 Agent 互通

效果：
  用户 A 对自己的 AI 说："帮我问一下 user-b 的 AI，他们项目进度怎么样了"
  Agent A 通过 sessions_send 给 Agent B 发消息
  Agent B 处理后回复
  Agent A 把结果告诉用户 A
```

不需要任何额外开发，只需要在配置中开启并设置允许列表。

但要注意：

- 这消耗双倍 token（A 和 B 各跑一次 AI）
- B 的回复取决于 B 的 Agent 的人设和可用信息
- 没有"B 的用户授权"这一步——是 Agent 层面的通信，不是用户层面的审批

### 场景五：公告广播（管理员通知所有用户）

**流程：**

```
管理员在后台输入公告内容
        │
        ▼
你的后端服务
        │
        ├── 方式 A：写文件
        │   遍历所有用户的 Workspace
        │   在每个 Workspace 写入 announcements.md
        │   Agent 下次运行时会看到这个文件
        │
        └── 方式 B：发消息
            遍历所有用户的 Agent
            通过 Gateway RPC 向每个 Agent 的主 Session 发一条消息
            Agent 会当作普通消息处理并回复"收到"之类的
```

两种方式各有适用场景：
- 写文件适合持久化的通知（Agent 每次启动都能看到）
- 发消息适合即时通知（一次性的，像推送一样）

## 五、共享权限怎么管

OpenClaw 内部**没有任何权限控制机制**来管理"谁能看谁的文件"。这完全是你的后端的责任。

建议的权限模型：

```
你的后端数据库

共享权限表：
┌──────────┬──────────┬──────────┬────────────┬──────────┐
│ 资源类型  │ 资源路径  │ 拥有者    │ 被分享者    │ 权限     │
├──────────┼──────────┼──────────┼────────────┼──────────┤
│ file     │ report   │ user-a   │ user-b     │ read     │
│ file     │ draft    │ user-a   │ user-c     │ read     │
│ folder   │ project  │ user-a   │ user-b,c   │ read     │
│ chat     │ conv-123 │ user-a   │ user-b     │ read     │
└──────────┴──────────┴──────────┴────────────┴──────────┘

每次共享操作的流程：
  1. 前端发起共享请求
  2. 你的后端检查权限表
  3. 权限通过 → 操作文件系统（复制/链接）
  4. 权限拒绝 → 返回错误
```

关键原则：**所有权限判断都在你的后端，OpenClaw 不参与决策。** OpenClaw 只负责"Agent 在自己的 Workspace 里干活"，至于 Workspace 里的文件是怎么来的、谁有权放进来的，它不关心。

## 六、方案总结

| 共享需求 | 实现方式 | 需要改 OpenClaw 吗 | 复杂度 |
|---------|---------|-------------------|-------|
| 文件共享 | 你的后端直接操作 Workspace 文件系统 | 不需要 | 低 |
| 公共知识库 | 共享目录 + 符号链接，或复制到每个 Workspace | 不需要 | 低 |
| 对话共享 | 你的后端读取 Session JSONL，存入自己的数据库 | 不需要 | 低 |
| Agent 间协作 | 开启 agentToAgent 配置 | 不需要（只需配置） | 零 |
| 公告广播 | 你的后端遍历 Workspace 写文件或发消息 | 不需要 | 低 |
| 协作编辑 | 需要你自己建一套协作编辑系统 | 不需要 | 高 |
| 细粒度权限控制 | 完全由你的后端管理 | 不需要 | 中 |

---

## 七、核心结论

**OpenClaw 不需要改造，共享体系建在你自己的后端。**

原因很简单：

1. **Workspace 是透明的** — 就是普通文件夹，你的后端可以直接读写
2. **Session 是透明的** — 就是 JSONL 文本文件，你的后端可以直接解析
3. **Agent 间通信已经有了** — `agentToAgent` 功能开箱即配

你不需要在 OpenClaw 里面做共享，你需要做的是在 OpenClaw 外面管理"谁的 Workspace 里该出现什么文件"。

用一个比喻总结：

> OpenClaw 是一排独立的办公室（每个用户一间），门锁由 OpenClaw 管。
> 你的后端是物业管理公司，负责决定"哪些快递可以送进哪间办公室"。
> 物业不需要改门锁的机制——它只需要有钥匙（文件系统访问权），并且知道哪些快递该送到哪里（权限表）。
