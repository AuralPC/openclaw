# 多用户、多会话与动态 Agent 解析

> 核心问题：能不能让每个用户开多个聊天会话，每个会话都像一个独立的 Agent，有自己的沙箱环境？

**答案：部分可以，但需要理解 OpenClaw 的设计哲学来找到正确的实现路径。**

---

## 一、先厘清三个概念

在讨论之前，必须先搞清楚三个容易混淆的概念：

| 概念 | 是什么 | 生命周期 | 创建方式 |
|------|--------|---------|---------|
| **Agent** | 一个完整的"大脑"，有独立的人格、记忆、权限 | 长期存在，配置在文件中 | 静态配置或 CLI 命令 |
| **Session** | 一次对话记录，类似于聊天窗口 | 可长可短，按需创建 | 消息进来时自动创建 |
| **Sandbox** | 一个隔离的执行环境（Docker 容器） | 按需创建，可自动清理 | 根据配置自动启动 |

用人来类比：

> - **Agent** 就像一个员工。他有自己的名字、性格、工位、工牌。
> - **Session** 就像这个员工接待的一个客户的对话记录本。他可以同时跟很多客户对话，每个客户一本记录本。
> - **Sandbox** 就像分配给员工的操作间。他在里面操作文件、执行命令，不会影响到别人的操作间。

---

## 二、你的需求拆解

你描述的场景是：

> 一个 AI 聊天网页，用户登录后可以开多个聊天会话。每个会话要相互隔离，有独立的执行环境。

把这个需求拆成几个子问题：

| 子问题 | 具体描述 |
|--------|---------|
| **多用户** | 不同用户的数据不能互相看到 |
| **多会话** | 同一个用户可以同时开多个聊天窗口 |
| **执行隔离** | 每个会话的代码执行、文件操作不互相影响 |
| **人格是否不同** | 每个会话的 AI 是否需要不同的性格/记忆 |

最后一个子问题——"人格是否不同"——是整个设计的**分水岭**。

---

## 三、场景 A：人格相同，只要执行隔离

> "每个会话用的是同一个 AI 人设，但我不希望会话 1 里创建的文件影响到会话 2。"

**这个场景 OpenClaw 原生支持，不需要动态创建 Agent。**

### 工作原理

OpenClaw 的沙箱有三种隔离粒度：

```
沙箱范围（scope）

"shared"   ──→  所有 Agent 的所有 Session 共用一个沙箱
                 ┌───────────────────────────┐
                 │        唯一的沙箱           │
                 │  Agent A 的会话1            │
                 │  Agent A 的会话2            │
                 │  Agent B 的会话1            │
                 └───────────────────────────┘

"agent"    ──→  同一个 Agent 的所有 Session 共用一个沙箱
                 ┌──────────────┐ ┌──────────────┐
                 │  Agent A 沙箱 │ │  Agent B 沙箱 │
                 │  会话1        │ │  会话1        │
                 │  会话2        │ │  会话2        │
                 └──────────────┘ └──────────────┘

"session"  ──→  每个 Session 独立一个沙箱 ✅ 你需要的
                 ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
                 │ 会话1   │ │ 会话2   │ │ 会话3   │ │ 会话4   │
                 │ 沙箱    │ │ 沙箱    │ │ 沙箱    │ │ 沙箱    │
                 └────────┘ └────────┘ └────────┘ └────────┘
```

当你把沙箱范围设为 `"session"` 时，系统会用每个会话的 Session Key 作为沙箱的唯一标识。不同会话自动获得不同的 Docker 容器，文件系统完全隔离。

### 架构示意

```
用户 A 登录你的前端
    │
    ├── 开启"会话 1"
    │       │
    │       ▼
    │   session key: agent:chat:my-chat:user-a:session-1
    │       → 分配 沙箱容器 #1
    │       → Agent "chat" 在容器 #1 中执行工具
    │
    ├── 开启"会话 2"
    │       │
    │       ▼
    │   session key: agent:chat:my-chat:user-a:session-2
    │       → 分配 沙箱容器 #2
    │       → Agent "chat" 在容器 #2 中执行工具
    │
    └── 两个会话共享同一个 Agent "chat" 的人格
        但执行环境完全隔离

用户 B 登录你的前端
    │
    └── 开启"会话 1"
            │
            ▼
        session key: agent:chat:my-chat:user-b:session-1
            → 分配 沙箱容器 #3
            → 跟用户 A 的任何容器都没有关系
```

### 关键点

- **Agent 只需要一个**（比如叫 "chat"），不需要为每个用户或每个会话创建新的 Agent
- **Session 是自动创建的**，消息进来时，如果对应的 Session Key 不存在，系统会自动建一个
- **沙箱是按需启动的**，第一次需要执行工具时才会创建容器
- **人格文件是共享的**，所有会话使用同一套 AGENTS.md、SOUL.md 等人设文件
- **聊天记录是隔离的**，每个 Session 有自己的 JSONL 文件

## 四、场景 B：每个会话需要不同的人格/记忆

> "我希望用户可以创建一个'严肃工作助手'会话和一个'轻松聊天伙伴'会话，两者人设完全不同。"

**这个场景需要不同的 Agent，因为人格文件（SOUL.md、AGENTS.md 等）是挂在 Agent 的 Workspace 下的。**

问题是：OpenClaw 的 Agent 是静态的，不支持运行时动态创建。

### 为什么 Agent 是静态的？

这不是技术限制，而是**设计选择**。理由：

1. **安全性** — 每个 Agent 都有自己的权限配置（能用哪些工具、能访问什么资源）。动态创建意味着权限也要动态分配，风险很高。

2. **可审计性** — 配置文件是声明式的，你可以一眼看出系统里有多少个 Agent、各自的权限边界。动态创建会让这变得不透明。

3. **资源可控** — 每个 Agent 都占用 Workspace 目录、可能有沙箱容器。不受限地动态创建可能导致资源失控。

系统内部有明确的校验逻辑：当收到一个消息时，它会检查消息指向的 Agent ID 是否在已注册的列表中，如果不在，直接拒绝。

### 现有架构下的折中方案

#### 方案一：预设有限的 Agent 模板

提前创建几个不同人设的 Agent，让用户从中选择：

```
预创建的 Agent：
  ├── "assistant"  → 通用助手人设
  ├── "coder"      → 编程助手人设
  ├── "writer"     → 写作助手人设
  └── "analyst"    → 数据分析人设

用户在前端选择人设类型
    → 你的渠道插件根据选择，在消息上下文中标记对应的路由信息
    → Binding 规则将消息路由到对应 Agent
```

优点是完全不需要改核心代码，符合现有架构。缺点是 Agent 数量有限，不支持用户自定义人设。

#### 方案二：一个 Agent + Session 级上下文注入

利用 OpenClaw 的系统提示词机制，在每个 Session 开始时注入不同的上下文：

```
Agent "chat" （唯一）
    │
    ├── 会话 1：系统提示词 = 通用人设 + "你是严肃的工作助手"
    ├── 会话 2：系统提示词 = 通用人设 + "你是轻松的聊天伙伴"
    └── 会话 3：系统提示词 = 通用人设 + "你是代码专家"
```

这可以通过 OpenClaw 的**插件钩子**实现——在 `before_agent_start` 阶段，根据 Session 的元数据来修改系统提示词。

优点是灵活度高，一个 Agent 就能模拟多种人格。缺点是"记忆"仍然是共享的（同一个 Workspace），需要在应用层做记忆隔离。

#### 方案三：二次开发，添加动态 Agent 创建接口

如果你确实需要完全独立的动态 Agent，需要在 Gateway 层面进行二次开发：

需要做的事情：

1. **新增 Gateway RPC 方法** — 添加类似 `agents.create` 的运行时接口
2. **动态写入配置** — 将新 Agent 注册到内存中的配置，并持久化
3. **动态创建 Workspace** — 为新 Agent 初始化目录和人设文件
4. **动态注册 Binding** — 让路由系统能找到新 Agent
5. **生命周期管理** — 处理 Agent 的过期、清理、资源回收

这个方案的工作量最大，但架构上是可行的，因为内部的多 Agent 基础设施（路由、Session、沙箱）已经很完善，缺的只是一个"运行时注册入口"。

## 五、三种方案对比

| 维度 | 方案一：预设 Agent | 方案二：Session 级注入 | 方案三：动态创建 Agent |
|------|-------------------|---------------------|---------------------|
| **开发量** | 零（纯配置） | 中（写插件钩子） | 大（改核心代码） |
| **人格隔离** | 完全隔离 | 提示词级别隔离 | 完全隔离 |
| **记忆隔离** | 完全隔离 | 需要应用层处理 | 完全隔离 |
| **灵活度** | 低（固定几种人设） | 高（可动态拼接提示词） | 最高 |
| **用户自定义人设** | 不支持 | 支持（通过提示词） | 支持 |
| **资源开销** | 固定（N 个 Workspace） | 最低（只有一个 Agent） | 动态增长 |
| **安全性** | 最高（静态审计） | 高 | 需要额外设计权限控制 |
| **适合场景** | 人设种类少且固定 | 人设多变但不需要深度隔离 | 真正需要完全动态的 Agent |

## 六、推荐的设计路径

根据你描述的场景（前端聊天页面、多用户多会话），我建议分阶段来做：

### 第一阶段：先跑通基本流程

- 创建一个 Agent（比如叫 "chat"）
- 写一个自定义渠道插件接入你的前端
- 配置 `sandbox.scope: "session"`，让每个会话有独立沙箱
- 此时已经实现了：多用户 + 多会话 + 执行环境隔离

### 第二阶段：加入人设差异化

- 如果人设种类有限（3~5 种），用方案一：预创建几个 Agent
- 如果人设需要灵活变化，用方案二：通过插件钩子在 Session 级别注入不同的提示词

### 第三阶段（如果需要）：真正的动态 Agent

- 只有当你确定需要"每个用户可以完全自定义 AI 的长期记忆和行为模式，且不同自定义之间需要物理隔离"时，才需要走方案三
- 这一步需要改核心代码，建议先把前两个阶段跑稳再考虑

## 七、一些容易踩的坑

### 坑 1：Agent ≠ Session，不要搞混

一个 Agent 下面可以有几百个 Session。不要为了"隔离"就去创建 Agent——先想想 Session 级隔离是否已经够用。

### 坑 2：沙箱容器不是免费的

`sandbox.scope: "session"` 意味着每个会话都会启动一个 Docker 容器。如果你有 1000 个并发会话，就是 1000 个容器。需要考虑：

- 服务器资源是否够用
- 容器的自动清理策略
- 沙箱的 prune（修剪）配置

### 坑 3：Session Key 的设计很重要

Session Key 的格式决定了会话的唯一性和路由。你的渠道插件在构造消息上下文时，需要合理设计发送者标识和会话标识：

```
好的设计：
  From = "user-001"（用户 ID）
  会话标识 = "session-abc"（前端生成的会话 ID）
  → session key: agent:chat:my-chat:user-001:session-abc

不好的设计：
  From = "anonymous"（所有用户都一样）
  → 所有用户的消息会混进同一个 Session
```

### 坑 4：子 Agent 不等于动态 Agent

子 Agent（Sub-Agent）是用来做后台并行任务的（比如"帮我调研一下这个问题"），它不是用来创建独立人格的。子 Agent 的特点：

- 运行完就结束，不是长期存在的
- 不能再派出子 Agent（防止嵌套失控）
- 默认不给它 session 相关工具
- 跟"用户自定义人设"是两回事

## 八、总结

| 你的需求 | 可行性 | 怎么做 |
|---------|-------|-------|
| 多用户数据隔离 | 原生支持 | 不同用户的消息天然走不同的 Session |
| 同一用户多个会话 | 原生支持 | 每个会话有独立的 Session Key |
| 每个会话独立执行环境 | 原生支持 | 配置 `sandbox.scope: "session"` |
| 不同会话不同人设（有限种类） | 原生支持 | 预创建多个 Agent + Binding 路由 |
| 不同会话不同人设（用户自定义） | 需要开发 | 插件钩子注入提示词，或二次开发动态 Agent |

OpenClaw 在"隔离"这件事上做得很扎实——Session 隔离、Agent 隔离、Sandbox 隔离，三层可以自由组合。大多数实际场景不需要动态创建 Agent，善用 Session + Sandbox 的组合就够了。
