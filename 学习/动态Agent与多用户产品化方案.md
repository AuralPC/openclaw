# 动态 Agent 与多用户产品化方案

> 核心目标：基于 OpenClaw 搭建一个多用户 AI 聊天产品，每个用户拥有独立的 AI 助手，用户之间完全隔离，同一用户的多个会话之间可以共享文件。

---

## 一、问题回顾：为什么需要"动态 Agent"

在前面的分析中，我们遇到了一个隔离粒度的缝隙：

```
OpenClaw 沙箱现有的三档：

  scope="shared"    所有人共用   → 用户之间不隔离，不行
  scope="agent"     同 Agent 共用 → 多用户路由到同一个 Agent 时，还是不隔离
  scope="session"   每会话独立   → 同一用户的不同会话之间也隔离了，太窄

我们需要的：
  "同一用户的会话共享，不同用户之间隔离"
```

解决方案的核心思路是：**把"用户"这个维度映射到"Agent"上。** 每注册一个用户，就创建一个专属 Agent。这样用 `scope="agent"` 就自然达成了"同用户共享、跨用户隔离"。

## 三、用户注册时发生了什么

当一个用户在你的网站完成注册，你的后端需要通知 OpenClaw 做四件事：

### 第 1 步：在配置中注册一个新 Agent

告诉 OpenClaw："从现在起，有一个叫 `user-10086` 的 Agent 了。"

这一步本质上就是在 OpenClaw 的配置文件中增加一条记录。就像在公司的通讯录里新增一个员工条目。

### 第 2 步：创建这个 Agent 的 Workspace

每个 Agent 需要一个"家"——一个专属的工作目录。系统会在这个目录里初始化一系列模板文件：

```
~/.openclaw/workspace-user-10086/
├── AGENTS.md      ← 这个用户的 AI 助手的行为规则
├── SOUL.md        ← 这个用户的 AI 助手的人格设定
├── USER.md        ← 关于这个用户的基本信息
├── IDENTITY.md    ← AI 助手的名字和风格
├── TOOLS.md       ← 工具使用说明
└── memory/        ← AI 助手对这个用户的记忆
```

这些文件之后可以被修改——比如用户在你的前端设置了"我希望 AI 说话幽默一些"，你就去更新这个用户对应 Agent 的 `SOUL.md`。

### 第 3 步：创建 Session 存储目录

会话记录需要有地方存放：

```
~/.openclaw/agents/user-10086/sessions/
├── （将来的会话文件会存在这里）
```

### 第 4 步：添加路由绑定

告诉 Gateway："以后从我的前端渠道来的、发送者标识为 `user-10086` 的消息，都交给 Agent `user-10086` 处理。"

## 四、用户聊天时发生了什么

注册完成后，用户开始使用你的 AI 聊天页面：

### 场景：用户开启第一个会话

```
用户在前端点击"新建对话"
        │
        ▼
前端生成一个会话 ID（比如 "conv-abc"）
        │
        ▼
用户输入"帮我写一首诗"
        │
        ▼
你的前端把消息发给你的渠道插件
  附带信息：
    发送者 = "user-10086"
    会话 = "conv-abc"
    内容 = "帮我写一首诗"
        │
        ▼
Gateway 路由匹配
  → 发送者 "user-10086" 命中路由规则
  → 指向 Agent "user-10086"
  → 生成 Session Key: agent:user-10086:my-chat:conv-abc
  → 这个 Session 不存在，自动创建
        │
        ▼
Agent "user-10086" 开始工作
  → 加载 Workspace 中的人设文件
  → 在自己的沙箱环境中执行
  → 生成回复："春风拂面花满枝……"
        │
        ▼
回复通过渠道插件返回给前端
```

### 场景：用户开启第二个会话

```
用户点击"新建对话"，得到会话 ID "conv-xyz"
        │
        ▼
消息路由到同一个 Agent "user-10086"
        │
        ▼
生成新的 Session Key: agent:user-10086:my-chat:conv-xyz
        │
        ▼
Agent "user-10086" 在同一个 Workspace 和沙箱中工作
  → 会话 conv-abc 里创建的文件，在 conv-xyz 里也能看到 ✅
  → 聊天记录是分开的（各自的 Session 文件） ✅
```

### 场景：另一个用户聊天

```
用户 B（user-20000）发消息
        │
        ▼
路由到 Agent "user-20000"
        │
        ▼
完全不同的 Workspace、不同的沙箱、不同的记忆
  → 看不到用户 A 的任何文件 ✅
  → 看不到用户 A 的任何聊天记录 ✅
```

## 五、隔离效果一览

| 维度 | 同用户不同会话 | 不同用户 |
|------|-------------|---------|
| 聊天记录 | 独立（每个 Session 一个文件） | 独立（不同 Agent 下） |
| 文件操作 | 共享（同一个沙箱容器） | 隔离（不同沙箱容器） |
| AI 人格 | 共享（同一个 SOUL.md） | 独立（各自的 Workspace） |
| AI 记忆 | 共享（同一个 memory/ 目录） | 独立（各自的 memory/） |
| 工具权限 | 共享（同一个 Agent 配置） | 可以不同（per-Agent 配置） |
| 执行环境 | 共享（sandbox scope="agent"） | 隔离（不同 Agent 不同容器） |

这正好是"同用户共享、跨用户隔离"的效果。

## 六、为什么这个方案可行

### 6.1 OpenClaw 的配置是"即时生效"的

Gateway 在处理每条消息时，都会重新从磁盘读取配置文件。这意味着：

> 你往配置里写入一个新 Agent → 下一条消息进来时 → Gateway 自动认识这个新 Agent

不需要重启服务，不需要发信号通知，不需要热加载机制——因为它本来就是每次都从磁盘读的。

### 6.2 Agent 创建的内部零件已经存在

创建 Agent 需要用到的所有函数（生成配置条目、创建目录、初始化文件、添加路由绑定）在代码里都已经实现好了，目前被 CLI 命令 `agents add` 使用。你只需要把同样的逻辑包装成一个 Gateway 可以接收的远程调用方法。

### 6.3 没有隐藏的"注册表"

Agent 的合法性校验只依赖配置文件中的 `agents.list` 数组。没有数据库、没有内存注册表、没有需要同步的额外状态。文件写了，Agent 就存在了。

## 七、需要开发的工作

### 必须做的

| 工作项 | 说明 |
|--------|------|
| **新增 `agents.add` RPC 方法** | 在 Gateway 的服务端方法中添加一个新的处理器，接收 agentId、workspace 路径等参数，执行创建逻辑 |
| **新增 `agents.delete` RPC 方法** | 用户注销时需要清理 Agent、Workspace、Sessions |
| **渠道插件** | 你的前端页面作为独立渠道接入 Gateway（参见《自定义渠道接入解析》） |
| **写入锁** | 多个用户同时注册时，需要排队写入配置文件，避免并发冲突 |

### 建议做的

| 工作项 | 说明 |
|--------|------|
| **人设定制接口** | 封装一个接口让前端能修改用户对应 Agent 的 SOUL.md、USER.md 等文件。这个接口其实已经有了（`agents.files.set`），只需要在你的后端调用 |
| **Agent 模板** | 准备一套默认的人设模板文件，新用户注册时用模板初始化 Workspace，避免冷启动时 AI 行为不稳定 |
| **用量统计** | 记录每个 Agent 的 token 消耗、会话数量等，用于计费或限额 |
| **空闲清理** | 长期不活跃的用户，可以归档其 Agent 的沙箱容器以节省资源，下次使用时再重建 |

## 八、方案的规模边界

### 适用规模：几十到几千用户

在这个范围内，方案运行良好：

- 配置文件只有几千条 Agent 记录，JSON5 文件大小在 KB 级别，读写无压力
- 每个 Workspace 只有几个小文本文件（加起来不到 100KB），磁盘开销很低
- 沙箱容器是按需启动的，不活跃的用户不占容器资源
- Gateway 单进程的瓶颈在 AI 模型调用，而非 Agent 数量

### 需要注意的上限

| 瓶颈 | 大约在什么规模出现 | 应对方式 |
|------|-------------------|---------|
| **配置文件读取变慢** | 数万条 Agent 记录时 | 将 Agent 注册从文件迁移到数据库 |
| **同时在线沙箱容器过多** | 数百个并发活跃用户 | 加入容器池管理，空闲超时自动释放 |
| **磁盘空间** | 取决于用户在沙箱中创建的文件量 | 设定 per-Agent 磁盘配额 |
| **单进程 Gateway 吞吐** | 高并发消息处理时 | 考虑多 Gateway 实例 + 负载均衡（需要更大的架构改造） |

### 不适用的场景

如果你计划做一个面向**公众的大规模 SaaS**（数万、数十万用户），这套"一人一 Agent + 配置文件"的方案会力不从心。那个阶段需要的是：

- Agent 注册存入数据库
- 路由规则动态查询而非静态匹配
- Workspace 存储走对象存储（S3 等）而非本地磁盘
- 多节点 Gateway 集群

但这已经超出了 OpenClaw 当前架构的设计范围，属于平台级改造。

## 九、用户生命周期完整流程

```
用户注册
    │
    ├── 1. 你的后端创建用户账号（你自己的用户表）
    ├── 2. 调用 Gateway → agents.add
    │       → 配置文件中新增 Agent
    │       → 创建 Workspace 目录 + 初始化人设文件
    │       → 创建 Session 目录
    │       → 添加路由绑定
    └── 3. 注册完成
            │
            ▼
用户使用
    │
    ├── 开启会话 → 自动创建 Session
    ├── 聊天 → Agent 在专属 Workspace 和沙箱中工作
    ├── 开新会话 → 新 Session，但共享同一个 Workspace 和沙箱
    ├── 定制 AI 性格 → 修改 Agent 的 SOUL.md
    └── 查看历史 → 读取对应 Session 的 JSONL 文件
            │
            ▼
用户注销
    │
    ├── 1. 调用 Gateway → agents.delete
    │       → 从配置文件中移除 Agent
    │       → 移除路由绑定
    ├── 2. 清理 Workspace 目录
    ├── 3. 清理 Session 文件
    ├── 4. 销毁沙箱容器
    └── 5. 你的后端删除用户账号
```

## 十、总结

这个方案的核心逻辑可以用一句话概括：

> **一个用户 = 一个 Agent = 一个独立的 AI 助手**

OpenClaw 已经把 Agent 隔离做得非常扎实（独立 Workspace、独立 Session、独立沙箱、独立认证）。我们要做的只是在"用户注册"和"Agent 创建"之间搭一座桥——一个 Gateway RPC 入口。

这座桥的开发量不大（本质上是把现有的 CLI 逻辑封装成网络接口），但带来的效果是把 OpenClaw 从一个"个人 AI 助手平台"变成一个"多用户 AI 助手平台"。在中小规模下，这是一条成本低、隔离强、架构清晰的路径。
