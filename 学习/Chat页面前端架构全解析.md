# OpenClaw Chat 页面前端架构全解析

> 本文面向有一定前端基础但不太熟悉 Web Components 的读者，用通俗的语言解释 Chat 页面是怎么运转的。

---

## 一、技术选型概览

OpenClaw 的前端**没有**使用 React、Vue 这类主流框架，而是选择了 **Lit**（一个轻量级 Web Components 库）+ **Vite**（构建工具）。

你可以把 Lit 理解为"原生浏览器组件的增强版"。浏览器本身支持自定义 HTML 标签（比如 `<my-button>`），Lit 只是让写这种自定义标签变得更方便——提供了响应式状态、模板语法等能力，但最终产出的还是标准的浏览器组件，不依赖虚拟 DOM。

样式方面用的是**纯 CSS**（非 Tailwind），通过 CSS 变量实现主题切换，支持深色/浅色模式。

---

## 二、整体页面结构

Chat 页面可以想象成一个"三明治"结构，从上到下分别是：

```
┌──────────────────────────────────────────────┐
│               顶部导航栏                       │
│         （Agent 选择、会话切换等）               │
├──────────────────────────────────────────────┤
│                                              │
│              消息展示区域                       │
│   （历史消息 + 正在流式输出的回复）              │
│                                              │
├──────────────────────────────────────────────┤
│            聊天输入区域                        │
│   （文本框 + 图片预览 + 发送按钮）              │
└──────────────────────────────────────────────┘
```

此外，右侧还有一个**可拖拽调节大小的侧边栏**，用于查看工具调用的详细输出（点击消息中的工具卡片即可打开）。

## 三、消息展示的逻辑

### 3.1 Slack 风格的消息分组

消息不是简单地一条条排列，而是采用了**类似 Slack 的分组机制**：

- 同一个角色（用户或助手）连续发送的多条消息会被归为一组
- 一组消息只显示一个头像，出现在第一条消息旁边
- 时间戳显示在这组消息的底部

这样做的好处是：当助手连续回复多段内容时，界面不会被重复的头像占满，阅读体验更清爽。

### 3.2 消息类型

展示区域里不只有纯文本，还会出现以下几种内容：

| 类型 | 说明 |
|------|------|
| 用户文本消息 | 用户输入的普通文字 |
| 用户图片消息 | 用户粘贴或上传的图片 |
| 助手文本消息 | AI 的回复，支持 Markdown 渲染 |
| 工具调用卡片 | 助手调用了某个工具（如搜索、代码执行等），以卡片形式展示 |
| 上下文压缩分隔线 | 标记 AI 在这里压缩了之前的对话上下文 |
| 流式输出指示器 | 三个跳动的圆点，表示助手正在"思考" |

### 3.3 Markdown 渲染与安全

助手的回复支持完整的 Markdown 格式（标题、列表、代码块、链接等）。渲染流程是：

1. 用 **marked** 库将 Markdown 文本转为 HTML
2. 用 **DOMPurify** 库对 HTML 进行消毒处理，过滤掉潜在的恶意脚本
3. 将安全的 HTML 插入页面

这个"先转换再消毒"的两步走是前端安全的标准做法，防止 AI 回复中可能包含的危险内容被浏览器执行。

## 四、消息收发机制

这是 Chat 页面最核心的部分。OpenClaw 使用 **WebSocket** 进行实时双向通信，而非传统的 HTTP 请求-响应模式。

### 4.1 为什么用 WebSocket？

传统 HTTP 就像"发短信"——你发一条请求，服务器回一条响应，然后连接就断了。而 WebSocket 像"打电话"——连接建立后双方可以随时说话，特别适合 AI 聊天这种需要**流式输出**（一个字一个字往外蹦）的场景。

### 4.2 发送消息的完整流程

当你按下回车发送一条消息时，背后发生了这些事：

```
用户按下回车
    │
    ▼
① 前端组装消息内容（文本 + 可能的图片附件）
    │
    ▼
② "乐观更新"——立刻在界面上显示你发的消息
   （不等服务器确认，先让用户看到，体验更好）
    │
    ▼
③ 通过 WebSocket 发送请求给后端
   请求格式类似：chat.send { text, attachments, sessionKey }
    │
    ▼
④ 界面进入"等待回复"状态
   显示三个跳动的圆点（reading indicator）
    │
    ▼
⑤ 后端开始处理，AI 开始生成回复
```

### 4.3 接收回复的流式过程

AI 的回复不是一次性返回的，而是像"打字机"一样一段段流出来：

```
后端推送 "chat" 事件
    │
    ├── state: "delta"（增量）
    │   → 把新文字追加到当前流式文本中
    │   → 界面实时更新，用户看到文字逐渐出现
    │   → 页面自动滚动到底部
    │   （这个过程可能重复数十次）
    │
    └── state: "final"（结束）
        → 清除流式状态
        → 从后端重新拉取完整的对话历史
        → 检查是否有排队中的消息需要发送
```

### 4.4 消息排队机制

如果你在 AI 还没回复完的时候又发了一条消息，这条消息不会丢失，而是进入一个**消息队列**。等当前回复结束后，队列中的消息会自动依次发送出去。每条排队消息都有唯一 ID 和时间戳，确保不会重复发送。

## 五、WebSocket 连接管理

WebSocket 连接并非一劳永逸，需要处理很多边界情况。

### 5.1 自动重连

网络抖动导致连接断开是常见场景。Gateway 客户端实现了**指数退避重连**：

- 第一次断开：等 800 毫秒后重连
- 每次失败后等待时间翻倍
- 最多等 15 秒
- 重连成功后重置等待时间

这样既能快速恢复连接，又不会在网络彻底断掉时疯狂重试。

### 5.2 设备身份认证

每个浏览器客户端在首次连接时会生成一对密钥（使用浏览器的 Web Crypto API），之后每次连接都用私钥签名来证明身份。这就像你的浏览器有了一张"身份证"，服务器能识别"这是同一个设备回来了"。

### 5.3 序列号与消息补漏

每条消息都有序列号。如果客户端发现收到的序列号不连续（比如从 5 直接跳到 8），说明中间有消息丢了，会触发补漏机制重新获取缺失的消息。

## 六、工具调用的实时展示

OpenClaw 的 AI 不仅能聊天，还能调用各种工具（搜索网页、执行代码、读写文件等）。这些工具调用的过程会实时展示在聊天界面中。

### 6.1 工具调用的生命周期

一次工具调用会经历三个阶段：

```
start（开始）
  → 显示工具名称和传入的参数
  → 卡片以"执行中"状态出现

update（更新，可选）
  → 工具正在运行，产出了部分结果
  → 卡片内容实时更新

result（完成）
  → 工具执行完毕，展示最终结果
  → 卡片切换为"已完成"状态
```

### 6.2 工具卡片

每个工具调用在聊天中以**卡片**形式展示，内容包括：

- 工具名称
- 调用参数（收起/展开）
- 执行结果摘要

点击卡片可以在右侧**侧边栏**中查看完整输出。侧边栏支持 Markdown 渲染，超长输出（超过 12 万字符）会被截断。

### 6.3 性能保护

为了防止大量工具调用拖慢页面：

- 同时最多展示 50 个工具卡片
- 更新频率限制在每 80 毫秒一次（节流）
- 这些限制对用户几乎无感知，但能有效防止页面卡顿

## 七、状态管理

### 7.1 没有 Redux，也没有 Zustand

OpenClaw 没有引入任何第三方状态管理库。所有状态都存在根组件 `OpenClawApp` 上，利用 Lit 自带的 `@state()` 装饰器实现响应式更新——当状态变化时，相关的 UI 会自动重新渲染。

### 7.2 核心状态一览

| 状态 | 含义 |
|------|------|
| chatMessages | 当前对话的全部历史消息 |
| chatStream | 正在流式输出的文本（没有流式输出时为空） |
| chatSending | 是否正在发送消息 |
| chatRunId | 当前请求的唯一标识，用于去重 |
| chatQueue | 排队等待发送的消息列表 |
| chatAttachments | 用户添加的图片附件 |
| toolStreamById | 正在执行的工具状态（按 ID 索引） |

### 7.3 数据流方向

状态的流动是**单向**的：

```
状态（State）
    │
    ▼
渲染函数（根据状态生成 UI）
    │
    ▼
用户交互（点击、输入等）
    │
    ▼
事件处理函数（修改状态）
    │
    ▼
状态变化 → 触发重新渲染（回到第一步）
```

这种单向数据流让程序的行为更可预测，调试也更容易。

## 八、聊天输入区域

### 8.1 输入框

聊天输入框是一个 `<textarea>` 元素，具备以下特性：

- **自适应高度**：随着输入内容增多，输入框自动变高
- **快捷键**：回车发送，Shift+回车换行
- **IME 兼容**：正确处理中文、日文等需要输入法的语言（在候选词选择期间不会误触发送）
- **连接感知**：当 WebSocket 断开时，输入框会被禁用

### 8.2 图片粘贴

你可以直接从剪贴板粘贴图片到输入框（比如截图后 Ctrl+V）。处理流程：

1. 检测到粘贴事件中包含图片数据
2. 将图片转为 Base64 编码的数据 URL
3. 在输入框上方显示图片缩略图预览
4. 每张图片旁边有删除按钮
5. 发送时图片和文字一起打包发出

支持同时添加多张图片。

## 九、会话（Session）管理

### 9.1 会话是什么？

一个"会话"就是一段完整的对话。你可以同时拥有多个会话，每个会话独立保存自己的消息历史。

### 9.2 会话标识

每个会话有一个 Key，格式类似 `agent:main:session:abc123`，包含了：

- 所属 Agent 的 ID
- 会话自身的 ID

当前活跃的会话 Key 会保存在浏览器的 LocalStorage 中，下次打开页面时自动恢复。

### 9.3 常用操作

| 操作 | 说明 |
|------|------|
| 切换会话 | 从下拉菜单选择另一个会话，界面加载对应的消息历史 |
| 新建会话 | 输入 `/new` 命令，创建一个全新的空白对话 |
| 重置会话 | 输入 `/reset`，清空当前会话 |
| 终止回复 | 输入 `/stop` 或 `stop`，中断 AI 当前的回复 |

### 9.4 历史消息加载

切换会话时，前端通过 WebSocket 发送 `chat.history` 请求，后端返回最近 200 条消息。如果历史消息超过 200 条，界面会显示一个提示，告知用户更早的消息已被隐藏。

## 十、多 Agent 支持

OpenClaw 支持多个 Agent（你可以理解为"不同性格/能力的 AI 角色"）。

### 10.1 Agent 切换

前端有一个 Agent 列表，每个 Agent 有自己的名称和头像。切换 Agent 相当于切换到一个完全不同的 AI，它有自己独立的会话列表。

### 10.2 Agent 与会话的关系

```
Agent A（主助手）
  ├── 会话 1（今天的工作讨论）
  ├── 会话 2（代码审查）
  └── 会话 3（方案设计）

Agent B（翻译助手）
  ├── 会话 1（论文翻译）
  └── 会话 2（邮件翻译）
```

每个 Agent 可以有多个会话，会话之间互不干扰。

---

## 十一、上下文压缩（Compaction）

AI 模型有上下文窗口限制——它能"记住"的对话长度是有上限的。当对话太长时，系统会自动压缩早期的对话内容。

### 11.1 用户感知

压缩发生时，聊天界面会显示一个提示条：

- 压缩进行中："Compacting context..."
- 压缩完成："Context compacted ✓"（5 秒后自动消失）

在消息列表中，压缩点会以一条分隔线标记，方便用户知道"这条线以上的内容 AI 可能记得不太清楚了"。

---

## 十二、侧边栏

### 12.1 功能

侧边栏主要用于查看工具调用的完整输出。比如 AI 调用了代码执行工具，侧边栏会显示完整的代码和运行结果。

### 12.2 交互

- **打开方式**：点击聊天中的工具卡片
- **调整大小**：拖动侧边栏和聊天区域之间的分隔条（宽度在 40%~70% 之间）
- **内容渲染**：支持 Markdown 格式
- **原始文本**：可以切换查看未格式化的原始输出

---

## 十三、滚动行为

一个看似简单但其实很讲究的细节：

- **新消息到来时**：如果用户正在查看底部（最新内容），自动滚动到最新消息
- **用户在回看历史**：如果用户往上翻看了旧消息，不会强制滚动到底部，避免打断阅读
- **流式输出期间**：随着文字逐渐出现，页面平滑滚动跟随

---

## 十四、复制功能

助手的每条消息旁边有一个"复制为 Markdown"按钮。点击后会将这条消息的内容以 Markdown 格式复制到剪贴板，方便粘贴到其他文档中使用。

## 总结

OpenClaw 的 Chat 页面虽然没有使用 React/Vue 这类主流框架，但架构清晰、职责分明：

- **Lit Web Components** 提供组件化能力
- **WebSocket** 实现实时双向通信和流式输出
- **单向数据流** 让状态变化可预测
- **消息队列** 保证消息不丢失
- **工具流式展示** 让 AI 的"思考过程"可视化
- **多 Agent + 多会话** 提供灵活的对话管理

整个系统的设计理念是：让用户能实时看到 AI 在做什么，而不是等一个黑盒给出最终结果。
