# OpenClaw 自定义渠道接入解析

> 核心问题：我能不能自己做一个前端聊天页面，然后把它当作一个独立渠道接入 OpenClaw？

**答案：可以，而且这是项目架构原生支持的做法。**

---

## 一、先理解"渠道"在 OpenClaw 里是什么

很多人一听到"接入 WhatsApp"、"接入 Telegram"，会觉得这些是系统内部硬编码的特殊通道。但在 OpenClaw 里不是这样的。

**每个渠道都是一个"插件"。** WhatsApp 是插件，Telegram 是插件，Slack 是插件，Discord 也是插件。它们跟你将要写的自定义前端，在架构层面是**完全平等的**。

用一个比喻来说：

> Gateway（网关）就像一个酒店的前台。WhatsApp、Telegram 这些渠道就像酒店跟不同旅行社的合作协议。每个旅行社用自己的方式把客人送过来（有的打电话预定，有的在线下单），但到了前台，处理流程是一样的：登记、分配房间、提供服务。
>
> 你要做的，就是签一个新的"旅行社合作协议"——也就是写一个新的渠道插件。

---

## 二、渠道插件需要回答哪几个问题

不管是 WhatsApp 还是你的自定义前端，每个渠道插件本质上只需要回答四个问题：

### 问题 1："你是谁？"—— 身份声明

每个渠道需要一个唯一的 ID 和基本描述信息。比如 Telegram 的 ID 就是 `"telegram"`，你的前端可以叫 `"my-chat"` 或任何你想要的名字。

这个 ID 会出现在路由规则（Binding）里，Gateway 通过它来识别消息来自哪个渠道。

### 问题 2："消息怎么进来？"—— 入站机制

这是最关键的部分：你的前端怎么把用户发的消息传给 OpenClaw？

现有渠道用了两种方式：

| 方式 | 原理 | 谁在用 |
|------|------|--------|
| **Webhook（HTTP 回调）** | 外部服务主动向 Gateway 发 HTTP 请求 | Google Chat、Mattermost |
| **长连接（轮询/WebSocket）** | 渠道插件主动连接外部服务，持续监听消息 | Telegram（轮询）、Discord（WebSocket） |

对于你自己的前端页面，最自然的方式是：

> 前端通过 HTTP 请求或 WebSocket 把消息发给 Gateway，Gateway 上运行的你的渠道插件负责接收并转交给路由系统。

不管用哪种方式，最终都是调用同一个核心函数——"消息调度器"（`dispatchInboundMessage`）。这个调度器是所有渠道共享的统一入口，它会：
1. 识别消息来自哪个渠道
2. 查路由表，决定交给哪个 Agent
3. 把消息排进对应 Agent 的处理队列

### 问题 3："回复怎么出去？"—— 出站机制

Agent 处理完消息后，需要把回复发回给你的前端。这就需要你告诉系统：

> "当你要给我的渠道发消息时，用这种方式发。"

比如 Telegram 的出站方式是调用 Telegram Bot API，WhatsApp 是调用 WhatsApp Business API。你的前端呢？可以是：

- 通过 WebSocket 推送给前端
- 把回复存起来，等前端来轮询获取
- 通过 HTTP 回调推给你的前端服务器

具体怎么做取决于你的前端架构，但对 OpenClaw 来说，它只关心"你提供了一个发送方法"。

### 问题 4："你能做什么？"—— 能力声明

每个渠道需要声明自己支持哪些功能，比如：

| 能力 | 说明 | 示例 |
|------|------|------|
| 聊天类型 | 支持私聊？群聊？频道？ | WhatsApp 支持私聊+群聊 |
| 多媒体 | 能发图片/视频/文件吗？ | 大多数渠道都支持 |
| 消息编辑 | 能修改已发送的消息吗？ | Telegram 支持，WhatsApp 不支持 |
| 流式输出 | 能逐字显示回复吗？ | 你的前端可以支持 |
| 表情回应 | 能给消息加 Reaction 吗？ | Slack/Discord 支持 |
| 话题/线程 | 支持消息线程吗？ | Slack/Telegram 支持 |

这些声明不影响核心功能，但会影响 Agent 的行为方式。比如如果你声明了不支持消息编辑，Agent 就不会尝试去编辑已发送的消息。

## 三、消息从前端到 Agent 的完整旅程

把上面四个问题串起来，一条消息的完整旅程是这样的：

```
用户在你的前端页面输入"今天天气怎么样"
          │
          ▼
    ┌──────────────┐
    │  你的前端页面  │
    │  （浏览器）    │
    └──────┬───────┘
           │  HTTP POST / WebSocket 发送
           ▼
    ┌──────────────────────┐
    │ 你的渠道插件           │  ← 运行在 Gateway 进程中
    │ （入站处理器）          │
    │                        │
    │ 做三件事：              │
    │ 1. 解析消息内容         │
    │ 2. 构造消息上下文       │
    │    （谁发的、从哪来的）  │
    │ 3. 交给消息调度器       │
    └──────────┬─────────────┘
               │
               ▼
    ┌──────────────────────┐
    │   消息调度器            │  ← OpenClaw 核心，所有渠道共享
    │  （dispatchInbound）   │
    │                        │
    │ 做两件事：              │
    │ 1. 查路由表             │
    │    channel="my-chat"   │
    │    → 匹配到 Agent X    │
    │ 2. 排队等候             │
    └──────────┬─────────────┘
               │
               ▼
    ┌──────────────────────┐
    │   Agent X 开始工作     │
    │                        │
    │ 1. 加载人设文件         │
    │ 2. 组装提示词           │
    │ 3. 调用 AI 模型         │
    │ 4. 可能调用工具          │
    │ 5. 生成回复             │
    └──────────┬─────────────┘
               │
               ▼
    ┌──────────────────────┐
    │ 你的渠道插件           │
    │ （出站处理器）          │
    │                        │
    │ 把回复发回你的前端      │
    └──────────┬─────────────┘
               │  WebSocket 推送 / HTTP 响应
               ▼
    ┌──────────────┐
    │  你的前端页面  │  显示"今天北京晴，最高温度25°C"
    └──────────────┘
```

## 四、路由表怎么配

一旦你的渠道插件注册好了（假设 ID 是 `"my-chat"`），在路由表里使用它就跟使用 WhatsApp 或 Telegram 完全一样：

**最简单的情况：** 所有来自你前端的消息都交给同一个 Agent

```
绑定规则：channel = "my-chat"  →  Agent "chat"
```

**区分用户：** 不同用户的消息交给不同 Agent

```
绑定规则：channel = "my-chat", peer = "user-001"  →  Agent "vip"
绑定规则：channel = "my-chat"                      →  Agent "chat"  （兜底）
```

**区分账号实例：** 如果你有多个前端实例（比如不同版本、不同站点）

```
绑定规则：channel = "my-chat", accountId = "prod"   →  Agent "main"
绑定规则：channel = "my-chat", accountId = "beta"   →  Agent "test"
```

路由优先级规则跟其他渠道完全一样：**越具体的规则越优先**。

## 五、跟现有 WebChat 的区别

OpenClaw 已经自带了一个叫 **WebChat** 的 Web 聊天界面。你可能会问：那我为什么还要自己做？

| 维度 | WebChat（内置） | 自定义渠道（你做的） |
|------|----------------|-------------------|
| **定位** | 管理/调试界面，附带聊天功能 | 独立的用户产品 |
| **架构身份** | 控制台 UI 的一部分，不是渠道 | 正式的消息渠道 |
| **路由能力** | 有限，不走完整的渠道路由 | 完整的 Binding 路由规则 |
| **多账号** | 不支持 | 支持（可以有多个前端实例） |
| **安全策略** | 依赖 Gateway 认证 | 可配置 DM 策略、白名单等 |
| **自定义程度** | 低，改样式需要改内置代码 | 高，完全你自己控制 |
| **适用场景** | 开发者自己用 | 面向终端用户的产品 |

**简单来说：** 如果你只是想有个网页跟 Agent 聊天，WebChat 够用了。但如果你要做一个面向用户的产品，有自己的登录体系、UI 设计、多用户隔离需求，那就应该做成独立渠道。

## 六、实际开发时的关注点

虽然这篇文档不写代码，但列出你在实际开发时需要关注的逻辑要点：

### 6.1 插件放在哪

OpenClaw 加载插件的顺序：

1. 配置文件中指定的路径
2. Workspace 目录下的 extensions 文件夹
3. 全局的 extensions 文件夹
4. 项目内置的 extensions 文件夹

你的插件放在任何一个位置都行，开发阶段建议放在 Workspace 下方便调试。

### 6.2 消息上下文需要提供什么

当你的前端发来一条消息时，你需要告诉调度器这些信息：

| 字段 | 含义 | 举例 |
|------|------|------|
| From | 发送者标识 | "user-001" |
| To | 接收方标识 | "agent" 或群组 ID |
| Channel | 渠道 ID | "my-chat" |
| MessageId | 消息唯一 ID | "msg-uuid-123" |
| 消息内容 | 文本/附件等 | "今天天气怎么样" |

这些信息是路由系统做匹配的依据。

### 6.3 多 Agent 共享同一个渠道

一个渠道可以通过 Binding 规则把不同的消息分给不同的 Agent。也就是说，你不需要为每个 Agent 做一个独立的前端——一个前端就够了，后台通过路由规则分流。

### 6.4 插件注册的两件事

每个渠道插件在加载时需要做两件事：

1. **注册渠道定义** — 告诉 Gateway"我是一个渠道，我的 ID 是 xxx，我能做 xxx"
2. **注册消息处理器** — 告诉 Gateway"当收到发给我的 HTTP 请求时，用这个方法来处理"

这两步完成后，你的前端在 OpenClaw 眼里就跟 Telegram 没有任何区别了。

---

## 七、总结

OpenClaw 的渠道体系是**插件化、平等化**的。WhatsApp 不比你的自定义前端"更原生"——它们都是插件，都遵循同一套接口，都通过同一个调度器处理消息。

你要做的事情在逻辑上很简单：

1. 写一个插件，声明"我是一个渠道"
2. 定义消息怎么进来（入站）
3. 定义回复怎么出去（出站）
4. 在路由表里加一条规则

之后，你的前端页面就是 OpenClaw 世界里的"一等公民"了。
