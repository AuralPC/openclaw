# OpenClaw 权限控制机制分析

本文档详细分析 OpenClaw 的权限控制系统，以及如何在多用户 AI 平台场景下进行适配。

## 1. 权限控制概览

OpenClaw 作为个人 AI 助手，设计了一套完善的权限控制体系来保护用户安全：


## 2. ExecSecurity - 命令执行安全模式

### 2.1 三级安全模式

ExecSecurity 控制 AI 是否可以执行系统命令：

```typescript
// 定义位置: packages/agent/src/security/exec-security.ts

type ExecSecurityMode = 'deny' | 'allowlist' | 'full';
```

| 模式 | 说明 | 使用场景 |
|------|------|---------|
| `deny` | 完全禁止执行任何命令 | 高安全环境，只允许对话 |
| `allowlist` | 只允许白名单中的命令 | 生产环境推荐 |
| `full` | 允许执行任何命令 | 开发/测试环境 |

### 2.2 工作流程

```
用户请求执行命令 "rm -rf /tmp/test"
           │
           ↓
┌──────────────────────────────────────┐
│      检查 ExecSecurity 模式          │
├──────────────────────────────────────┤
│                                      │
│  mode === 'deny'?                    │
│      │                               │
│      ├─ 是 → 直接拒绝执行 ❌          │
│      │                               │
│      └─ 否 → 继续检查               │
│                │                     │
│                ↓                     │
│  mode === 'allowlist'?               │
│      │                               │
│      ├─ 是 → 检查命令白名单          │
│      │       │                       │
│      │       ├─ 匹配 → 允许执行 ✅    │
│      │       └─ 不匹配 → 触发 ExecAsk │
│      │                               │
│      └─ 否 (full) → 允许执行 ✅      │
│                                      │
└──────────────────────────────────────┘
```

## 3. ExecAsk - 用户确认机制

### 3.1 三种确认模式

当命令不在白名单中时，ExecAsk 控制是否询问用户：

```typescript
type ExecAskMode = 'off' | 'on-miss' | 'always';
```

| 模式 | 说明 | 行为 |
|------|------|------|
| `off` | 不询问 | 白名单外的命令直接拒绝 |
| `on-miss` | 白名单外询问 | 白名单内直接执行，白名单外询问用户 |
| `always` | 总是询问 | 任何命令都需要用户确认 |

### 3.2 用户交互流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    ExecAsk 用户确认流程                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  AI 想执行命令: npm install lodash                              │
│           │                                                     │
│           ↓                                                     │
│  ┌─────────────────────────────────────┐                       │
│  │ ExecAsk 模式检查                     │                       │
│  ├─────────────────────────────────────┤                       │
│  │ off:      命令在白名单？             │                       │
│  │           是 → 执行 | 否 → 拒绝      │                       │
│  │                                     │                       │
│  │ on-miss:  命令在白名单？             │                       │
│  │           是 → 执行 | 否 → 询问用户  │                       │
│  │                                     │                       │
│  │ always:   直接询问用户               │                       │
│  └─────────────────────────────────────┘                       │
│           │                                                     │
│           ↓ (需要询问时)                                        │
│  ┌─────────────────────────────────────┐                       │
│  │ 向用户发送确认请求                   │                       │
│  │                                     │                       │
│  │ "AI 想执行以下命令：                 │                       │
│  │  npm install lodash                 │                       │
│  │                                     │                       │
│  │  [允许] [拒绝] [允许并加入白名单]"   │                       │
│  └─────────────────────────────────────┘                       │
│           │                                                     │
│           ↓                                                     │
│  用户响应 → 执行/拒绝/更新白名单                                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 4. Command Allowlist - 命令白名单

### 4.1 白名单配置

白名单支持通配符匹配，可以灵活控制允许的命令：

```yaml
# 配置示例
security:
  exec:
    mode: allowlist
    allowlist:
      - "git *"           # 允许所有 git 命令
      - "npm *"           # 允许所有 npm 命令
      - "pnpm *"          # 允许所有 pnpm 命令
      - "node *"          # 允许所有 node 命令
      - "cat *"           # 允许查看文件
      - "ls *"            # 允许列出目录
      - "mkdir *"         # 允许创建目录
      # 危险命令不加入白名单
      # - "rm *"          # 不允许删除
      # - "chmod *"       # 不允许修改权限
      # - "sudo *"        # 不允许提权
```

### 4.2 通配符匹配规则

```
┌─────────────────────────────────────────────────────────────────┐
│                    命令匹配示例                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  白名单规则: "git *"                                            │
│                                                                 │
│  ✅ 匹配:                                                       │
│     git status                                                  │
│     git commit -m "message"                                     │
│     git push origin main                                        │
│     git log --oneline                                           │
│                                                                 │
│  ❌ 不匹配:                                                     │
│     GIT status          (大小写敏感)                            │
│     gitk                 (不是 git 命令)                        │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  白名单规则: "npm install *"                                    │
│                                                                 │
```

## 5. Owner-Only Tools - 敏感工具限制

### 5.1 概念说明

某些工具只允许 "owner" 身份的发送者调用，防止非授权用户触发敏感操作：

```typescript
// 工具定义中的 ownerOnly 标记
const whatsappLoginTool = {
  name: 'whatsapp_login',
  description: '登录 WhatsApp 账号',
  ownerOnly: true,  // 只有 owner 可以调用
  // ...
};
```

### 5.2 Sender 身份验证

```
┌─────────────────────────────────────────────────────────────────┐
│                    Owner-Only 工具调用流程                       │
├─────────────────────────────────────────────────────────────────┤

│           │                                                     │
│           ↓                                                     │
│  ┌─────────────────────────────────────┐                       │
│  │ AI 选择调用 whatsapp_login 工具      │                       │
│  └─────────────────────────────────────┘                       │
│           │                                                     │
│           ↓                                                     │
│  ┌─────────────────────────────────────┐                       │
│  │ 检查工具是否标记为 ownerOnly        │                       │
```

## 6. Elevated Mode - 权限提升

### 6.1 概念说明

Elevated Mode 允许临时提升权限，但有严格的来源限制：

```typescript
interface ElevatedConfig {
  enabled: boolean;
  allowFrom: string[];  // 允许提升权限的来源白名单
  timeout: number;      // 权限提升的超时时间（秒）
}
```

### 6.2 工作流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    Elevated Mode 权限提升                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  场景：用户需要执行需要更高权限的操作                            │
│                                                                 │
│  1. 检查是否启用 Elevated Mode                                  │
│     │                                                           │
│     ├─ enabled: false → 无法提升权限                            │
│     │                                                           │
│     └─ enabled: true → 继续                                     │
│                │                                                │
│                ↓                                                │
│  2. 检查请求来源是否在 allowFrom 白名单                         │
│     │                                                           │
│     │  allowFrom: ["telegram:123456", "webchat:owner"]          │
│     │                                                           │
│     ├─ 来源匹配 → 允许提升                                      │
│     │                                                           │
│     └─ 来源不匹配 → 拒绝提升                                    │
│                │                                                │
│                ↓                                                │
│  3. 设置权限提升超时                                            │
│     │                                                           │
│     │  elevatedUntil = now + timeout                            │
│     │                                                           │
│     ↓                                                           │
│  4. 在超时前，用户具有提升后的权限                              │
│     │                                                           │
│     │  超时后自动恢复到普通权限                                 │
│     │                                                           │
└─────────────────────────────────────────────────────────────────┘
```

### 8.4 跨 Session 文件访问限制

OpenClaw 原生不支持跨 session 文件访问限制，需要自定义实现：

```typescript
// 自定义路径校验中间件示例
class PathAccessGuard {
  constructor(private userId: string, private baseDir: string) {}

  validatePath(requestedPath: string): boolean {
    // 规范化路径
    const normalizedPath = path.normalize(requestedPath);

    // 检查是否在用户目录内
    const userDir = path.join(this.baseDir, this.userId);

    if (!normalizedPath.startsWith(userDir)) {
      throw new SecurityError(
        `Access denied: ${requestedPath} is outside user directory`
      );
    }

    return true;
  }
}

// 在文件操作工具中注入
const readFileTool = {
  name: 'read_file',
  execute: async (params, context) => {
    const guard = new PathAccessGuard(context.userId, '/user-data');
    guard.validatePath(params.path);

    // 继续原有逻辑
    return fs.readFile(params.path, 'utf-8');
  }
};
```

### 8.5 多用户权限配置模板

```yaml
# 用户级别权限配置模板
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-{{userId}}-openclaw-config
data:
  config.yaml: |
    security:
      exec:
        mode: allowlist
        ask: on-miss
        allowlist:
          - "git *"
          - "npm *"
          - "node *"
          - "cat *"
          - "ls *"

      elevated:
        enabled: false  # 多用户环境建议禁用

      tools:
        # 禁用可能影响其他用户的工具
        disabled:
          - system_reboot
          - network_config
          - process_kill

    paths:
      # 限制文件访问范围
      allowedPaths:
        - "/user-data/{{userId}}/**"
        - "/shared/readonly/**"

      deniedPaths:
        - "/etc/**"
        - "/var/**"
        - "/user-data/*/**"  # 其他用户目录
```

### 9.2 推荐配置

```yaml
# 生产环境推荐配置
security:
  exec:
    mode: allowlist         # 白名单模式
    ask: on-miss            # 白名单外询问用户
    allowlist:
      - "git status"
      - "git diff *"
      - "git log *"
      - "git add *"
      - "git commit *"
      - "npm install"
      - "npm run *"
      - "node *"
      - "cat *"
      - "ls *"
      - "pwd"
      # 不包含: rm, chmod, chown, sudo, curl, wget 等

  elevated:
    enabled: false          # 多用户环境禁用权限提升

  audit:
    enabled: true
    level: detailed
    retention: 30d
```

## 10. 总结

### 10.1 OpenClaw 权限控制要点

| 机制 | 作用 | 多用户适配 |
|------|------|-----------|
| **ExecSecurity** | 控制命令执行权限 | 每用户独立配置 |
| **ExecAsk** | 用户确认危险操作 | 保留，提升安全性 |
| **Command Allowlist** | 限制可执行命令 | 每用户独立白名单 |
| **Owner-Only Tools** | 限制敏感工具 | 确保正确的身份验证 |
| **Elevated Mode** | 临时权限提升 | 建议禁用 |
| **Security Audit** | 操作审计记录 | 必须启用 |

### 10.2 核心理解

```
┌─────────────────────────────────────────────────────────────────┐
│                    权限控制核心原则                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 最小权限原则                                                │
│     • 默认拒绝，显式允许                                        │
│     • 只授予完成任务所需的最小权限                              │
│                                                                 │
│  2. 用户确认原则                                                │
│     • 危险操作需要用户明确确认                                  │
│     • 不在白名单的操作询问用户                                  │
│                                                                 │
│  3. 隔离原则                                                    │
│     • 用户间完全隔离                                            │
│     • Session 间默认隔离                                        │
│                                                                 │
│  4. 可审计原则                                                  │
│     • 所有敏感操作留痕                                          │
│     • 支持事后追溯                                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```
