# Docker 部署与安全防护策略

> 前置背景：在前面的方案中，我们设计了"一个用户一个 Agent"的多用户架构，并且确定了"后端直接操作 Workspace 文件系统"来实现共享。这一切的前提是 OpenClaw 的数据目录通过 Docker Volume 挂载到宿主机上。本文讨论这种挂载方式带来的安全风险以及应对策略。

---

## 一、先理解数据住在哪

### 不挂载 Volume 的情况（默认）

```
宿主机
│
└── Docker 容器（OpenClaw）
        │
        └── 容器内部文件系统
              └── ~/.openclaw/
                    ├── openclaw.json         ← 配置
                    ├── workspace-user-001/   ← 用户数据
                    ├── agents/               ← 会话记录
                    └── credentials/          ← 认证信息
```

所有数据都在容器**内部**。容器就像一个密封的盒子：

- 外面（宿主机、你的后端）看不到里面的文件
- 盒子一扔（容器销毁），里面的东西全没了

### 挂载 Volume 之后

```
宿主机
│
├── /data/openclaw/          ← 数据实际在宿主机磁盘上
│     ├── openclaw.json
│     ├── workspace-user-001/
│     ├── agents/
│     └── credentials/
│
└── Docker 容器（OpenClaw）
        │
        └── 容器内看到的 ~/.openclaw/
              │
              └── 其实指向宿主机的 /data/openclaw/（同一份数据）
```

挂载之后，容器内外看到的是**同一份文件**。容器里的 AI 写了一个文件，宿主机上立刻能看到；你的后端在宿主机上改了一个文件，容器里的 AI 下次读取时也能看到。

**这正是前面方案能工作的基础，但也是安全风险的来源。**

---

## 二、风险在哪

核心问题是：**AI Agent 在容器内有文件操作能力，而这些文件实际存在于宿主机上。**

AI Agent 是一个由大语言模型驱动的程序，它能通过 OpenClaw 提供的工具（读文件、写文件、执行命令等）来操作文件系统。虽然 AI 通常是按照人设指令乖乖干活的，但理论上它可能因为"理解错误"或"被恶意提示词诱导"而做出意料之外的操作。

### 风险分级

```
风险等级：低
┌──────────────────────────────────────────────────────┐
│ AI 突破 Docker 容器，直接控制宿主机操作系统            │
│                                                        │
│ 为什么低：Docker 的容器隔离是操作系统级别的，            │
│ AI 通过 OpenClaw 的工具无法绕过这层隔离。              │
│ 它只能看到容器内部的文件系统 + 挂载进来的目录。         │
│ 宿主机的系统文件、其他容器、网络服务，它都碰不到。      │
└──────────────────────────────────────────────────────┘

风险等级：中
┌──────────────────────────────────────────────────────┐
│ AI 误删或破坏 Workspace 中的用户文件                   │
│                                                        │
│ 为什么中：AI 确实有写文件和执行命令的权限，              │
│ 如果它"理解错了"用户意图，可能删掉重要文件。            │
│ 由于 Volume 挂载，删除会直接反映到宿主机磁盘上。        │
└──────────────────────────────────────────────────────┘

风险等级：中
┌──────────────────────────────────────────────────────┐
│ AI 写入大量文件，耗尽宿主机磁盘空间                     │
│                                                        │
│ 为什么中：容器内的 AI 写文件，实际写入的是宿主机磁盘。   │
│ 如果不设限制，一个失控的 AI 可能写出几十 GB 的垃圾文件， │
│ 导致宿主机磁盘满，影响宿主机上的所有服务。              │
└──────────────────────────────────────────────────────┘

风险等级：中低
┌──────────────────────────────────────────────────────┐
│ AI 消耗过多 CPU 或内存，拖慢宿主机                      │
│                                                        │
│ 为什么中低：容器内运行的进程最终还是用宿主机的资源。      │
│ 如果不设资源限制，一个 Agent 执行了高消耗命令，           │
│ 可能影响同机器上的其他服务。                             │
└──────────────────────────────────────────────────────┘

风险等级：低
┌──────────────────────────────────────────────────────┐
│ 用户 A 的 AI 访问用户 B 的文件                          │
│                                                        │
│ 为什么低但需注意：如果两个用户的 Workspace 都挂载在       │
│ 同一个容器里，AI 理论上可以用绝对路径去访问别人的目录。   │
│ OpenClaw 的沙箱机制可以防止这一点。                      │
└──────────────────────────────────────────────────────┘
```

## 三、三层防护体系

应对这些风险，需要三层防护叠加使用。每一层解决不同维度的问题。

### 第一层：Docker 容器层 —— 控制"AI 能碰到什么"

Docker 容器本身就是第一道防线。关键策略：

**只挂载必要的目录**

```
推荐的挂载方式：

✅ 只挂 ~/.openclaw/         → AI 只能碰这个目录
❌ 不要挂 /                   → 否则 AI 能看到整个宿主机
❌ 不要挂 /home               → 否则 AI 能看到宿主机用户的个人文件
❌ 不要挂 /etc 或 /var        → 否则 AI 能碰到系统配置和日志
```

**部分目录可以只读挂载**

不是所有目录都需要让 AI 有写权限：

| 目录 | 挂载方式 | 理由 |
|------|---------|------|
| 配置文件（openclaw.json） | 只读 | AI 不应该能修改系统配置。动态创建 Agent 时，由你的后端写入，不经过 AI |
| 认证信息（credentials/） | 只读 | AI 不应该能篡改 API 密钥 |
| 用户 Workspace（workspace-*/） | 读写 | AI 需要在这里工作 |
| 会话记录（agents/*/sessions/） | 读写 | AI 需要读写聊天记录 |

**设置资源上限**

| 资源 | 限制建议 | 作用 |
|------|---------|------|
| 内存 | 根据用户规模设定（如 4GB~16GB） | 防止内存耗尽导致宿主机卡死 |
| CPU | 限制使用的核心数（如 2~4 核） | 防止一个容器独占 CPU |
| 磁盘 | 限制挂载目录的可用空间 | 防止 AI 写满磁盘 |

磁盘限制有两种做法：

- 把 `~/.openclaw/` 放在一个独立的磁盘分区上，分区满了不会影响系统分区
- 或者使用 Docker 的存储驱动限制（取决于具体的存储驱动支持情况）

### 第二层：OpenClaw 沙箱层 —— 控制"AI 能做什么"

OpenClaw 自身有一套沙箱机制，可以在 Docker 容器内部再套一层限制。

**沙箱的核心理念**

```
没有沙箱：
  AI → 直接操作 OpenClaw 容器的文件系统（= 挂载的宿主机目录）

有沙箱：
  AI → 操作沙箱容器的文件系统（隔离环境）
       沙箱容器有自己的文件系统
       Workspace 可以选择性挂入沙箱（只读/读写/不挂）
```

**Workspace 访问模式**

OpenClaw 的沙箱对 Workspace 有三种访问级别：

| 模式 | AI 能做什么 | 适用场景 |
|------|-----------|---------|
| `"rw"`（读写） | AI 可以自由读写 Workspace 中的文件 | 需要 AI 创建和修改文件的场景 |
| `"ro"`（只读） | AI 只能读 Workspace 中的文件，不能修改 | 只需要 AI 参考文件但不改动的场景 |
| `"none"`（不可见） | AI 完全看不到真正的 Workspace，只能在沙箱临时目录里操作 | 最严格的隔离，AI 的文件操作不影响真实 Workspace |

**工具权限控制**

除了文件系统层面的限制，还可以直接关闭某些工具：

| 工具 | 关闭后的效果 |
|------|------------|
| 关闭 `write` | AI 不能创建或覆盖文件 |
| 关闭 `edit` | AI 不能编辑已有文件 |
| 关闭 `exec` | AI 不能执行命令行命令 |
| 关闭 `apply_patch` | AI 不能打补丁修改文件 |

比如一个"只聊天不干活"的 Agent，可以把写入和执行类工具全部关闭，这样它连碰文件的能力都没有。

**跨用户访问防护**

如果不开沙箱，同一个 OpenClaw 容器里的 AI 理论上可以用绝对路径去访问其他用户的 Workspace（因为它们都在同一个容器内）。

开启沙箱后，每个 Agent（或每个 Session）被限制在自己的沙箱容器中，看不到其他 Agent 的文件。这就是前面讨论的 `sandbox.scope` 的作用：

```
scope = "agent"   → 同一用户的所有会话共享一个沙箱，看不到其他用户的
scope = "session" → 每个会话一个独立沙箱，连同一用户的不同会话都隔离
```

### 第三层：你的后端应用层 —— 控制"出事了怎么办"

即使有前两层防护，也需要你的后端做好最后一道保障：

**定期备份**

```
备份策略示意：

  每天凌晨：备份所有 Workspace
      ~/.openclaw/workspace-*/ → /backup/daily/YYYY-MM-DD/

  每次重要操作前：快照
      用户修改人设 → 先备份当前版本

  保留策略：最近 7 天的每日备份 + 每月一份月度备份
```

就算 AI 把文件搞乱了，你也能恢复到之前的状态。

**磁盘监控**

```
监控项：
  ├── 总磁盘使用率 → 超过 80% 告警
  ├── 单个用户 Workspace 大小 → 超过阈值告警
  └── 增长速率 → 短时间内暴增告警（可能是 AI 在刷文件）
```

**操作审计（可选）**

如果安全要求高，可以在你的渠道插件或后端记录 AI 的关键操作：

```
审计日志：
  [2026-02-09 14:30] user-001 / session-abc / Agent 写入文件 report.md (2.3KB)
  [2026-02-09 14:31] user-001 / session-abc / Agent 执行命令 python analyze.py
  [2026-02-09 14:32] user-001 / session-abc / Agent 删除文件 temp.txt
```

## 四、不同安全级别的配置方案

根据你的产品对安全性的要求，可以选择不同的防护组合：

### 宽松模式 —— 适合内部工具、开发环境

```
Docker：
  └── 挂载 ~/.openclaw/（读写）

OpenClaw：
  └── 沙箱关闭
  └── 所有工具开放

你的后端：
  └── 每日备份

风险：AI 可以自由操作文件，但只在挂载目录范围内
适合：信任用户、用户量少、容错能力强的场景
```

### 标准模式 —— 适合多用户产品

```
Docker：
  ├── 配置文件和认证信息只读挂载
  ├── Workspace 和 Session 读写挂载
  ├── 设置内存和 CPU 上限
  └── 挂载目录放在独立分区

OpenClaw：
  ├── 沙箱开启，scope = "agent"（per-user 隔离）
  ├── workspaceAccess = "rw"（AI 可以在自己的空间内操作）
  └── 按 Agent 类型配置工具权限

你的后端：
  ├── 每日备份 + 关键操作前快照
  ├── 磁盘监控和告警
  └── per-Agent 存储配额

风险：AI 只能操作自己 Agent 的文件，不能跨用户，资源有上限
适合：面向真实用户的产品
```

### 严格模式 —— 适合对安全要求高的场景

```
Docker：
  ├── 所有目录只读挂载，写操作通过你的后端中转
  ├── 严格的资源限制
  ├── 网络隔离（只允许访问 AI 模型 API）
  └── 挂载目录放在加密分区

OpenClaw：
  ├── 沙箱开启，scope = "session"（每个会话独立）
  ├── workspaceAccess = "ro" 或 "none"
  ├── 关闭 exec 工具（AI 不能执行命令）
  └── 关闭 write/edit 工具（AI 不能修改文件）

你的后端：
  ├── 实时备份
  ├── 全量操作审计
  ├── 异常行为检测
  └── 严格的存储配额

风险：AI 基本只能聊天，不能操作任何文件或执行任何命令
适合：处理敏感数据、合规要求高的企业场景
```

## 五、一个容易忽略的问题：沙箱嵌套

如果你同时使用了 Docker 部署 OpenClaw **和** OpenClaw 自身的沙箱功能，就会出现"容器套容器"的情况：

```
宿主机
└── Docker 容器（OpenClaw 主进程）       ← 第一层容器
      └── 沙箱容器（Agent 的执行环境）   ← 第二层容器
            └── AI 在这里执行命令和操作文件
```

这需要 OpenClaw 的 Docker 容器能够创建和管理内部的沙箱容器（通常通过挂载 Docker Socket 或使用 Docker-in-Docker 方案）。

这带来额外的配置复杂度，但也带来更强的隔离：

- 第一层容器隔离了 OpenClaw 进程与宿主机
- 第二层沙箱容器隔离了各 Agent（各用户）之间

如果你觉得双层容器太复杂，另一个选择是：**只用 Docker 部署，不开 OpenClaw 的沙箱**。这时隔离完全依赖 Docker 层 + 工具权限控制。对于大多数场景来说也够用了。

## 六、总结

| 问题 | 结论 |
|------|------|
| Volume 挂载会不会让 AI 搞崩宿主机？ | 不会搞崩系统，但可能耗尽磁盘或删除用户文件 |
| 怎么防止磁盘被撑爆？ | Docker 资源限制 + 独立磁盘分区 + 你的后端做存储配额 |
| 怎么防止文件被误删？ | OpenClaw 沙箱限制写权限 + 你的后端做定期备份 |
| 怎么防止用户 A 看到用户 B 的文件？ | OpenClaw 沙箱 scope="agent"，每个用户隔离在自己的沙箱里 |
| 需要三层防护全开吗？ | 不一定，根据你的产品安全要求选择合适的组合 |

一句话总结：

> **Docker 管住边界（AI 能碰到什么），OpenClaw 沙箱管住行为（AI 能做什么），你的后端管住后果（出事了怎么恢复）。三层各管一件事，不重叠、不遗漏。**
